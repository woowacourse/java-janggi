# 미션 중 기록
### 기능 추가로 인해 수정한 위치 개수
- 추가가 아닌 '수정'을 기준으로 즉, 기존에 없던 코드를 새로 생성하는 것이 아니라 기존 작성했던 코드를 지우고 로직을 다시짜는 경우를 수정으로 취급겠다.
- 궁성 이동 : 궁성 이동 규칙을 다루는 별도의 도메인을 추가한 것을 제외하면,
  - 기존 이동 규칙만 쓰던 메서드가 궁성 규칙도 고려하도록 수정하면서 기물 별 moveStrategy를 분기처리 하는 코드
  - 그리고 실제로 루트를 생성하는 Piece의 createRoute만 영향을 받았다. (총 3곳)
- 점수 규칙 : 기존 기물들을 가져와서 점수 규칙을 정의한 정책 객체, 그 값을 활용하여 계산하는 계산 객체를 추가한 것을 제외하고 기존 코드의 수정을 보면
  - 점수 연산 결과를 매턴 출력하기 위해 GameRunner와 OutputView 2곳만 수정이 있었다.
- 게임 종료 방식 & 게임 복구 : 게임 상태 도입, 새 게임 생성 분리, H2 저장/복구 연결을 제외하고도, 
  - 기본적인 게임 흐름 처리를 Runner가 전부 하던 상태에서 DB와 새로운 게임 상태 객체에 의존하게 되면서 Board에서 기물 이동 시 판단해야 할 조건이 추가되고, 그로 인한 동작도 추가되면서 `GameRunner`, `Main`, `Board`, `TurnManager`4곳에 큰 수정

### 사이클1 때보다 수정 범위가 줄었는가/늘었는가
- 줄었다고 생각한다. 기본적으로 기능과 확장, 수정에 용이한 코드를 하기 위해 독립적으로 책임을 지도록 설계를 진행하였는데 실제로 기능을 추가할 때 해당 기능을 위한 도메인을 제외하면 흐름 처리를 위한 코드 수정 외에는 가장 많은 책임을 지고 도메인 핵심 역할을 하는 엔티티인 보드 정도만 수정이 존재하였는데, 이는 사이클1에서 보드의 역할이 보다 확장되면서 불가피 했다고 생각한다. 이를 제외한 코드는 새로운 기능 추가나 변경에 영향을 받지 않고 수정 범위를 최소화 한 상태에서 사이클2 작업을 진행할 수 있었다고 생각했다.

### 도메인과 저장소를 분리한 코드 1곳
- `domain.game.GameRepository` 인터페이스를 두고, 실제 H2 구현은 `database.H2GameRepository`로 분리했다.

### DB 변경 시 도메인 코드 영향 분석
- DB 스키마 변경이 발생해도 도메인은 `GameStatus`, 현재 턴, 보드 스냅샷만 알면 된다. 저장 형식이 바뀌어도 영향은 주로 `H2GameRepository`와 `schema.sql`에만 나타날 것으로 예상된다.
