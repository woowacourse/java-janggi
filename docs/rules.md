
### 기존 규칙
[테스트 규칙]
```
1. 테스트는 메서드가 아닌 기능(하나의 역할) 단위로 작성한다
2. 테스트를 위해 private 접근 제한자를 변경하지 않는다. 
   - private 메서드는 public 메서드를 통해 간접적으로 검증한다.
3. private 메서드를 직접 테스트하고 싶다면 책임 분리를 의심한다.
4. public 메서드로도 검증되지 않는 private 로직은 기능을 재정의한다.
5. getter/setter와 단순 파싱 로직은 별도로 테스트하지 않는다.
6. 입출력, 컨트롤러 등 어플리케이션 계층은 테스트하지 않는다.
7. 숨은 의존성으로 테스트가 어렵다면 외부 주입으로 개선을 시도한다.
8. 테스트 코드 내부에 조건문을 넣지 않고 케이스를 분리한다.
9. 메서드에 분기가 있다면 경계값과 분기별 테스트를 나눠 작성한다.
```
[책임 분리 규칙]

	1. 객체는 자신의 상태를 기반으로 스스로 행동하며, 함께 변하는 것은 함께 두고 따로 변하는 것은 분리한다.
	2. 다른 이유로 변경되는 코드는 서로 다른 책임으로 보고 분리한다.
	3. 객체의 상태는 객체 스스로 변경하도록 하고 외부에서 직접 변경하지 않는다.
	4. 데이터를 꺼내 판단하지 않고, 객체에게 상태 변경/요약의 행동을 위임한다.
	5. 로직을 외부에서 처리하기 위해 값을 반환한다면 책임 분리를 의심한다.
	6. 관련 로직이 객체 외부에 있다면 객체 내부로 이동하거나 구조를 재설계한다.
	7. 도메인 객체는 UI, 입출력, 프레임워크에 의존하지 않도록 한다.
	8. import를 통해 불필요한 의존이 있는지 확인하고 책임이 과하지 않은지 점검한다.
	9. 일급 컬렉션이 처리해야 할 로직이 외부에 있지 않은지 확인한다.

[리펙토링 규칙]

	1. 역할/책임 분리를 가장 먼저 수행한다.
	2. 조건문 분기를 축소한다.
	3. 중복 로직을 제거한다.
	4. 숨은 의존을 제거한다.
	5. 검증 로직이 필요한 필드 값은 Value Object로 만들어 클래스로 감싼다.
	6. 상수화할 수 있는 값은 상수화한다.
	
### 새로운 규칙
[상태 위치 규칙] : 어떤 상태를 어떤 객체가 가지는가?
```
- 객체의 행위를 먼저 정의하고, 그 행위가 다루는 상태는 객체 내부에서 관리한다.
```

[불변 객체 기준] : 언제 불변으로 만드는가
```
- 최초 생성 이후, 객체 내부의 상태 변경이 되면 안 되거나 외부에서 변경하지 않는 경우, 불변 객체 사용을 고려할 수 있다.
- 객체의 상태(프로퍼티)를 기준으로 동등성이 판단된다면, 불변 객체 사용을 고려할 수 있다.
```
[캡슐화 기준] : 무엇을 숨기는가
```
- 객체 내부의 상태와 본인만 알아야 하는 행위를 숨기고, 외부에서 직접 상태를 변경할 수 없도록 한다.
- 외부에는 협력에 필요한 메소드와 상태에 대한 간략 요약 혹은 연산 결과만 노출한다.
```

[null 사용 기준]
```
- null 사용은 최대한 지양하며, 대신 명시적으로 알아볼 수 있는 별도의 타입(객체)을 사용한다.
- 불가피하게 null을 사용하는 경우에는 Optional 등으로 안전하게 감싸거나 검증을 거치고 사용한다.
```

[조건문 대체 기준] - 언제 다형성으로 바꾸는가
```
- 공통된 행위나 정보를 가진 여러 객체들이 하나의 범주에 묶이거나, 중복되는 상태·행위가 발생할 때 다형성을 고려할 수 있다.
- 하나의 객체 안에서 여러 상태를 관리하는 로직이 많아져 분리가 필요할 때, 공통 행위를 객체별로 다르게 수행하도록 다형성으로 바꿀 수 있다.
```
[역할/인터페이스 설계 기준]
```
- 중복되는 행위가 발생할 때 내부 속성이 아닌 행위(메소드)를 기준으로 인터페이스를 먼저 정의하고, 공통된 것들을 역할과 행위로 추상화한다.
- 공통 행위를 객체별로 다르게 구현하거나, 상황에 따라 구현체를 다르게 조립하고 싶을 때 인터페이스를 활용한다.
```
[새 타입 추가 시 변경 범위 제한 규칙]
```
- 새로운 타입이 추가될 때는 추상체(인터페이스 등)가 있는지 먼저 확인하고, 가능한 해당 객체 내부와 생성하는 곳만 변경한다.
- 추상체가 있다면 새 타입 외에 다른 변경이 발생하지 않도록 하고, 다른 객체에 영향을 준다면 리팩토링을 고려한다.
```
