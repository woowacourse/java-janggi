## 기능 요구 사항

### 1.1단계 - 보드 초기화

- 게임 시작 시 장기판과 전체 기물을 올바른 위치에 초기화한다.
- 1.1단계에서는 기물의 이동은 구현하지 않는다.

### 1.2단계 - 기물 이동

- 각 기물의 이동 규칙을 구현한다.
- 기물의 이동 규칙은 직접 요구사항을 분석하여 정의한다.
- **궁성(宮城) 영역은 구현하지 않는다.** (사이클2에서 다룬다)

## 기능 목록 (테스트 명세)

### 1.1단계: 보드 및 기본 도메인 초기화

#### 위치 (Position)

- [x] x 좌표가 0 미만이거나 8 초과이면 예외가 발생한다
- [x] y 좌표가 0 미만이거나 9 초과이면 예외가 발생한다
- [x] 올바른 x, y 좌표가 주어지면 객체가 정상적으로 생성된다

#### 진영 (Side)

- [x] 진영은 초와 한만 가진다

#### 플레이어 (Player)

- [x] 턴 상태를 토글하면 현재 턴 여부가 반전된다
- [x] 플레이어는 상대방의 기물을 선택하면 예외가 발생한다

#### 플레이어들 (Players)

- [x] 초기 플레이어 생성 시 두 플레이어의 이름이 같으면 예외가 발생한다

#### 기물 공통 (Piece)

- [x] 주어진 진영과 자신의 진영이 같은지 올바르게 판별한다

#### 장기판 초기화 (BoardFactory / Board)

- [x] 선택한 포메이션에 맞게 32개의 기물이 초기 위치에 정확히 배치된다
- [x] 양 진영의 궁이 지정된 궁성 위치에 정상적으로 배치된다

### 1.2단계: 기물 이동 및 게임 상태

#### 궁 (General)

- [x] 궁은 상 하 좌 우 1칸 이동할 수 있다 (OneStepStrategy)

#### 사 (Guard)

- [x] 사는 상 하 좌 우 1칸 이동할 수 있다 (OneStepStrategy)

#### 졸 (Soldier)

- [x] 초나라 졸은 상 좌 우 1칸 이동할 수 있다 (OneStepStrategy)
- [x] 한나라 졸은 하 좌 우 1칸 이동할 수 있다 (OneStepStrategy)

#### 마 (Horse)

- [x] 마는 직선 1칸 이동 후 대각선 1칸 방향으로 이동할 수 있다 (SequenceStrategy)
- [x] 마는 직선 1칸 경로에 장애물 기물이 존재하면 해당 방향으로 이동할 수 없다

#### 상 (Elephant)

- [x] 상은 직선 1칸 이동 후 대각선 2칸 방향으로 이동할 수 있다 (SequenceStrategy)
- [x] 상은 직선 1칸 또는 대각선 1칸 경로 중 하나라도 장애물 기물이 존재하면 이동할 수 없다

#### 차 (Chariot)

- [x] 차는 상 하 좌 우 방향으로 장애물을 만날 때까지 연속해서 이동할 수 있다 (ContinuousStrategy)
- [x] 차는 이동 경로 중 아군 기물을 만나면 그 직전 위치까지만 이동할 수 있다
- [x] 차는 이동 경로 중 적군 기물을 만나면 해당 위치까지 이동하여 잡을 수 있다

#### 포 (Cannon)

- [x] 포는 상 하 좌 우 방향으로 기물 하나를 뛰어넘어 빈칸으로 이동할 수 있다
- [x] 포는 이동 경로에서 포 기물을 뛰어넘을 수 없다
- [x] 포는 기물을 뛰어넘은 후 적군 기물을 만나면 해당 위치까지 이동하여 잡을 수 있다 (ContinuousStrategy)
- [x] 포는 뛰어넘은 후 만난 적군 기물이 포일 경우 잡을 수 없다

#### 장기판 이동 (Board)

- [x] 목적지에 적군 기물이 있으면 보드에서 해당 기물을 제거하고 이동한다
- [x] 목적지에 아군 기물이 있으면 이동할 수 없다
- [x] 기물이 존재하지 않는 빈 좌표를 출발지로 입력하면 예외가 발생한다

#### 게임 상태 및 흐름 (Game)

- [x] 기물 이동이 완료되면 턴이 상대방 진영으로 변경된다
- [x] 이동할 수 있는 목적지가 전혀 없는 기물을 선택하면 예외가 발생한다
- [x] 선택한 기물이 이동할 수 없는 위치를 목적지로 입력하면 예외가 발생한다
- [x] 보드에 궁이 하나만 남게 되면 게임은 종료 상태가 된다

### 1.3단계: 사용자 입력 및 파서 검증

#### 플레이어 이름 입력

- [x] 이름이 2글자 미만이거나 5글자를 초과하면 예외가 발생한다
- [x] 이름에 빈 값이나 공백만 입력되면 예외가 발생한다

#### 포메이션(마, 상) 옵션 입력

- [x] 포메이션 입력이 1, 2, 3, 4 일 때 정상 동작한다
- [x] 포메이션 입력이 1, 2, 3, 4 중 하나가 아니면 예외가 발생한다

#### 위치 입력

- [x] 올바른 좌표 형식이 입력되는 경우 정상 동작한다
- [x] 위치 입력 포맷이 `(x, y)` 형태가 아니면 예외가 발생한다
- [x] 위치 입력 포맷 내의 좌표에 숫자가 아닌 값이 포함되면 예외가 발생한다

## 구조 및 설계

- [x] 이동 방향(Direction) 분리: 상, 하, 좌, 우 등 x/y 증감값을 갖는 Enum 구현
- [x] 이동 전략(Strategy) 분리: `OneStepStrategy`, `ContinuousStrategy`, `SequenceStrategy` 구현 및 각 기물에 주입
- [x] 플라이웨이트 팩토리(PieceFactory): 위치 상태가 없는 불변 기물 객체를 싱글톤/캐싱하여 반환
- [x] 보드 캡슐화(BoardReader): 기물이 보드의 맵 자료구조에 직접 접근하지 못하도록 읽기 전용 인터페이스 도입
- [x] 불변 맵 복사: 보드 이동 시 `Map.copyOf()`를 사용하여 불변 맵 반환

# 사이클2: 미션 (기물 확장 + DB 적용)

> 규칙을 적용하면서 장기에 새로운 요구사항을 추가하고 DB를 연동한다.

### 2.1단계 - 기물의 확장 (궁성 및 승패, 점수)

- 사이클1에서 제외했던 **궁성(宮城)** 영역의 규칙을 포함하여 기물의 이동을 구현한다.
- 상대방의 왕(궁)을 잡았을 때 게임을 즉시 종료하고 승패를 판정한다.
- 현재 남아 있는 기물에 대한 점수 계산 기능을 구현한다. (대한장기협회 룰 적용)

### 2.2단계 - DB 적용

- **필수:** 애플리케이션을 재시작하더라도 이전에 하던 장기 게임을 다시 시작할 수 있도록 DB를 연동한다.
- **필수:** DB를 적용할 때 도메인 객체의 변경을 최소화하며, 도메인과 저장소를 분리한다.
- **선택:** 장기 게임방을 만들고 특정 방에 입장할 수 있는 기능을 추가한다.
- **필수 기록:** 변경된 위치 개수, 수정 범위 비교, 도메인/저장소 분리 및 변경 코드 영향 분석 기록.

---

### 2.1단계: 기물 확장 (궁성, 승패, 점수)

#### 궁성 (Palace) 도메인

- [x] 특정 좌표가 초나라 또는 한나라의 궁성 영역 내부인지 올바르게 판별한다.
- [x] 궁성 경계 바로 밖의 좌표는 궁성 내부가 아닌 것으로 판별한다.
- [x] 궁성 내의 특정 좌표가 주어졌을 때, 해당 위치에서 이동 가능한 대각선 방향(Direction)들을 반환한다.
- [x] 궁성 영역 밖의 좌표에 대해서는 대각선 방향을 반환하지 않는다(빈 리스트 반환).

#### 장기판 공간 정보 확장 (BoardReader)

- [x] 기물의 배치가 아닌, 장기판 특정 좌표의 기하학적 공간 정보(대각선 유무)를 제공한다.

#### 기물 제약 (Piece 행동 반경)

- [x] 궁은 이동 경로 탐색 시 자신의 궁성 영역을 벗어날 수 없다.
- [x] 사는 이동 경로 탐색 시 자신의 궁성 영역을 벗어날 수 없다.
- [x] 궁과 사를 제외한 기물은 이동 경로 탐색 시 궁성 밖의 좌표도 정상적으로 목적지에 포함한다.

#### 기물 대각선 이동 로직 (Strategy + Palace 조합)

- [x] 궁은 궁성 내 대각선 경로가 존재하는 위치에서 해당 대각선 방향의 1칸 이동 경로를 추가한다.
- [x] 사는 궁성 내 대각선 경로가 존재하는 위치에서 해당 대각선 방향의 1칸 이동 경로를 추가한다.
- [x] 차는 궁성 내 대각선 경로를 만나면 해당 대각선 방향으로 끝까지 연속 이동하는 경로를 생성한다.
- [x] 포는 궁성 내 대각선 경로에 위치한 기물을 뛰어넘어 반대편으로 이동하는 경로를 생성한다.
- [x] 졸과 병은 궁성 내 대각선 중 자신의 진영 기준 전진 방향과 일치하는 대각선으로만 1칸 이동 경로를 추가한다.

#### 승패 판정 및 게임 상태

- [x] 목적지에 상대방의 '궁'이 있어 잡게 되는 순간, 게임이 종료된다.
- [x] 게임이 종료된 상태에서 기물을 이동하려고 시도하면 예외가 발생한다.

#### 점수 계산 (Score)

- [x] 각 기물의 고유 점수를 정확히 반환한다 (차 13, 포 7, 마 5, 상 3, 사 3, 졸/병 2).
- [x] 현재 보드에 남아있는 양 진영의 기물을 바탕으로 총 점수를 합산하여 올바르게 계산한다.
- [x] 한나라는 후공의 보상(덤)으로 1.5점을 추가로 부여받는다.

### 2.2단계: DB 적용 및 영속성 관리

#### 패키지 및 아키텍처 개편

- [x] 도메인, UI, 인프라 로직이 `janggi` 최상위 패키지 아래에 역할별로 분리된다.
- [x] 컨트롤러는 비즈니스 로직을 직접 수행하지 않고 `GameService`에게 처리를 위임한다.

#### 데이터베이스 및 레포지토리 (JDBC)

- [x] 데이터베이스 커넥션을 생성한다.
- [x] 데이터베이스에 `game` 테이블과 `piece` 테이블이 정상적으로 생성된다.
- [x] `GameRepository`는 `Game` 애그리거트 루트 단위로만 데이터를 저장(`save`)하고 조회(`findById`)한다.
- [x] 저장(Save): 새로운 장기 게임이 시작되거나 턴이 끝날 때, 현재의 장기판 상태와 턴 정보가 DB에 정상적으로 반영된다.
- [x] 조회(Find): DB에 저장된 `game`과 `piece` 데이터를 읽어와 메모리 상의 `Game` 객체로 재조립(Rehydrate)한다.

#### GameDao (게임 메타데이터 접근)

- [x] 새로운 게임 정보를 DB에 저장하고, 자동 생성된 게임 ID를 반환한다.
- [x] 특정 게임 ID를 입력받아 DB에서 해당 게임 정보를 조회한다.

#### PieceDao (기물 상태 접근)

- [x] 특정 게임 ID에 속한 기물 목록을 DB에 일괄 저장(INSERT)한다.
- [x] 특정 게임 ID를 입력받아 DB에 저장된 해당 게임의 모든 기물 목록을 조회(SELECT)한다.
- [x] 특정 게임 ID를 입력받아 DB에 저장된 해당 게임의 모든 기물을 삭제(DELETE)한다.

#### 영속성이 부여된 게임 흐름 (GameService)

- [x] 게임을 한 턴 진행하고 애플리케이션을 강제 종료한 뒤 다시 실행해도, 마지막 상태부터 게임을 이어서 진행할 수 있다.
- [x] (예외 시나리오) 기물을 이동할 수 없는 위치로 이동하려다 예외가 발생한 경우, DB의 상태는 이전 턴의 상태를 그대로 유지한다 (저장되지 않는다).

#### 방 만들기 및 입장 (선택)

- [ ] 새로운 게임 방을 생성하고 해당 방에 대한 고유 정보를 부여할 수 있다.
- [ ] 생성된 게임 방의 목록을 조회하고, 특정 방을 선택해 게임을 진행할 수 있다.

## 입출력예시

1. 게임 시작 모드를 입력 받는다.

   ```
   장기 게임을 시작합니다.
   1: 새로운 게임 시작
   2: 기존 게임 이어하기
   ```

   2번 선택 시

   ```
   [저장된 게임 목록]
   ID: 4 | aaa vs bb | 현재 턴: CHO
   ID: 3 | aa vs bb | 현재 턴: CHO
   ID: 2 | 고래 vs 제이콥 | 현재 턴: HAN
   ID: 1 | 고래 vs 제이콥 | 현재 턴: CHO
   ```

2. 초나라 플레이어의 이름을 입력받는다.
3. 초나라 플레이어의 기물 배치를 입력받는다.

   ```
   기물 배치를 선택하세요.
   1. 상마상마
   2. 마상마상
   3. 상마마상
   4. 마상상마
   ```

4. 한나라 플레이어 이름을 입력받는다.
5. 한나라 플레이어의 기물 배치를 입력받는다.

   ```
   기물 배치를 선택하세요.
   1. 상마상마
   2. 마상마상
   3. 상마마상
   4. 마상상마
   ```

6. 초나라 플레이어부터 한 턴씩 진행
   1. 보드판 출력

   2. 플레이어가 선택할 수 있는 기물의 위치를 입력받는다.

      ```
      (보드판 출력)
      이동 시킬 기물의 위치를 입력하세요. ex) 0, 3
      ```

   3. 선택한 기물의 목적지를 입력받는다.

      ```
      선택한 기물이 이동할 수 있는 위치입니다. 이동할 위치를 입력하세요. ex) 0, 3
      (x, y), (x, y), ...
      ```

   4. 왕이 잡히면 게임 종료
      ```
      제이콥(이/가) 승리했습니다.
      ```

## 프로그래밍 요구 사항

## 팀 규칙

> [!abstract] ### **1. 상태 위치 규칙**
>
> (If-Then) 만약 기물의 위치가 이동, 잡힘, 배치 변경처럼 게임판 전체 상태 변화와 함께 바뀐다면
>
> → 위치 정보는 보드가 관리하고, 기물은 자신의 위치를 직접 가지지 않는다
>
> (기준) 상태 소유 기준: 변경의 책임이 있는 객체가 그 상태를 소유한다
>
> (금지) 이번 미션에서 보드와 기물이 동시에 위치 상태를 가지지 않는다
>
> ---
>
> ### **2. 불변 객체 기준**
>
> (If-Then) 만약 기물이 가지는 정보가 종류, 소속 팀, 이동 규칙처럼 게임 도중 바뀌지 않는 값이라면
>
> → 기물 객체는 불변으로 만든다
>
> (기준) 불변성 판단 기준: 게임 도중 변하지 않는 정보는 객체 내부에서 변경 불가능해야 한다
>
> (금지) 이번 미션에서 기물의 종류, 팀, 이동 규칙을 생성 후 변경하지 않는다
>
> ---
>
> ### **3. 캡슐화 기준**
>
> (If-Then) 만약 어떤 상태를 외부에서 직접 수정 시 규칙 위반이나 정합성 문제가 생긴다면
>
> → 그 상태는 내부에 캡슐화하고, 책임 있는 객체만 변경할 수 있게 한다
>
> (If-Then) 만약 보드의 내부 상태가 외부 로직에 그대로 노출되면
>
> → 보드의 상태는 직접 수정 가능한 형태로 공개하지 않고, 필요한 동작만 메서드로 제공한다
>
> (기준) 캡슐화 기준: 정합성을 깨뜨릴 수 있는 내부 표현과 수정 권한은 숨긴다
>
> (금지) 이번 미션에서 보드의 내부 상태를 외부에서 직접 수정하지 않는다
>
> ---
>
> ### **4. null 사용 기준**
>
> (If-Then) 만약 빈 칸도 보드 위의 의미 있는 상태라면
>
> → 빈 칸은 null 대신 객체 또는 존재 여부가 드러나는 방식으로 표현한다
>
> (If-Then) 만약 빈 칸 여부를 자주 검사해야 한다면
>
> → null 검사에 의존하기보다, 빈 상태를 명시적으로 표현하는 구조를 우선한다
>
> (기준) null 사용 기준: 없음도 의미 있는 상태라면 명시적으로 표현한다
>
> (금지) 이번 미션에서 빈 칸을 단순 null 검사에만 의존하여 처리하지 않는다
>
> ---
>
> ### **5. 조건문 대체 기준**
>
> (If-Then) 만약 조건문이 객체의 종류에 따라 동작을 나누기 위해 사용된다면
>
> → 조건문 대신 다형성을 우선 고려하고, 각 객체가 자신의 규칙을 직접 구현한다
>
> (If-Then) 만약 조건문이 보드 범위 확인, 장애물 확인, 같은 팀 여부 확인처럼 객체 종류와 무관한 공통 검증이라면
>
> → 이런 조건문은 공통 로직으로 유지한다
>
> (기준) 다형성 적용 기준: 같은 질문에 객체마다 다른 답을 해야 하면 다형성 후보로 본다
>
> (금지) 이번 미션에서 기물 타입을 문자열, enum, switch/if로 반복 분기하여 이동 규칙을 처리하지 않는다
>
> ---
>
> ### **6. 역할/인터페이스 설계 기준**
>
> (If-Then) 만약 여러 객체가 같은 행위를 해야 하지만 구현 방식은 서로 다르다면
>
> → 공통 인터페이스를 정의해 무엇을 할 수 있는가를 통일한다.
>
> (기준) 인터페이스 설계 기준: 호출 방식은 통일하고, 구현 방식은 각 객체에 위임한다.
>
> (금지) 이번 미션에서 호출하는 쪽이 기물 종류를 먼저 판별한 뒤 각 규칙을 직접 실행하지 않는다.
>
> ---
>
> ### **7. 새 타입 추가 시 변경 범위 제한 규칙**
>
> (If-Then) 만약 새 기물이 추가될 때 기존 이동 로직을 여러 곳 수정해야 한다면
>
> → 기물별 책임 분리가 부족한 것으로 보고 구조를 꼭 필히 다시 점검한다.
>
> (기준) 확장성 판단 기준: 새로운 기물 추가나 규칙 변경 시 기존 코드 수정 범위가 작아야 한다.
>
> (금지) 이번 미션에서 새 기물 추가를 위해 기존 분기문을 계속 늘리는 방식으로 확장하지 않는다

> ### **8. 도메인/저장소 분리 기준**
>
> (If-Then) 만약 도메인 객체가 DB 연결 정보나 SQL 쿼리를 직접 알고 있다면
>
> → Repository 인터페이스를 도입하여 도메인 로직과 데이터 액세스 로직을 엄격히 분리한다.
>
> (기준) 분리 기준: "도메인 객체는 메모리 상에서만 존재하며, 프로그램 종료 시 초기화되는 순수 로직에 집중한다."
>
> (금지) Board, Piece 등 도메인 엔티티 내부에서 java.sql 패키지의 클래스를 직접 참조하거나 의존하지 않는다.
>
> ---
>
> ### **9. 저장 경계 규칙**
>
> 저장소의 호출은 도메인 비즈니스 로직을 조율하는 다른 계층의 책임이다.
>
> (If-Then) 만약 저장/조회 로직이 장기판의 이동 로직이나 승패 판정 로직과 섞여 있다면
>
> → 서비스(Service) 계층을 도입하여 도메인 객체에 행위를 시킨 후, 그 결과를 저장소에 전달한다.
>
> (기준) 저장 경계 기준: 도메인은 자신의 상태를 변경할 뿐, 저장되는 시점과 방법은 서비스가 결정한다.
>
> (금지) 컨트롤러나 도메인 객체가 직접 Repository의 세부 구현체(예: JdbcRepository)를 생성하거나 관리하지 않는다.
>
> ---
>
> ### **10. 저장 시점 규칙**
>
> 데이터의 변경은 의미 있는 행위가 완료된 시점에 즉시 반영되어야 한다.
>
> (If-Then) 만약 게임 도중 비정상적인 종료에도 데이터가 유지되어야 한다면
>
> → 매 턴 종료(기물 이동 성공) 시점마다 변경된 상태를 DB에 저장한다.
>
> (If-Then) 만약 특정 행위(이동, 잡기 등)가 도중 실패하거나 예외가 발생한다면
>
> → 데이터를 저장하지 않고 이전 상태를 유지하는 트랜잭션 롤백 원칙을 적용한다.
>
> (기준) 저장/조회 시점: 성공적인 행위 단위(Transaction Unit)의 종료 시점에 저장하고, 애플리케이션 시작 또는 '이어하기' 요청 시점에 조회한다.
>
> (금지) 도메인 로직이 수행되는 중간 단계(예: 유효성 검사 직후, 이동 전)에서 불완전한 데이터를 DB에 반영하지 않는다.

### 👨‍💻 고민과 결정 (나는 왜 이렇게 구현할까?)

**1. 기물과 보드의 협력 설계: 내부 자료구조 노출 방지와 책임 할당**

- **고민:** 기물이 이동 가능 위치를 찾으려면 보드의 상태(빈칸, 아군/적군 위치)를 알아야 한다. 기존처럼 `Map<Position, Piece>`를 기물에게 직접 넘기면 보드의 내부 구현이 노출되고 캡슐화가 깨진다. 반대로, 기물이 보드 상태를 아예 모른 채 '이동 경로(Route)' 데이터만 반환하고 외부 심판(Validator)이 이를 판정하게 만드는 것이 맞을까?

- **결정:** 보드 내부 구조를 추상화한 `BoardReader` 인터페이스를 기물에게 주입하는 방식을 선택했다.

- **근거:** 첫째, 기물이 `Map`이라는 보드의 세부 구현에 강하게 의존하는 구조를 탈피하고 싶었다. 둘째, 외부 심판(Validator) 방식을 도입하기에는 마(馬), 상(象)처럼 기물마다 확인해야 할 경유지(멱)의 개수가 다르고 포(包)처럼 예외적인 규칙도 많다. 이 모든 경우의 수를 외부 심판 하나에 위임하면 심판 객체의 책임이 너무 무거워지고 비대해진다. `BoardReader`를 도입하면 보드의 실제 자료구조는 완벽히 숨기면서도, 각 기물이 자신의 고유한 이동 규칙을 객체지향적으로 응집도 있게 캡슐화할 수 있다

**2. 상태 변경과 불변성: `move` 시 가변 Map 갱신 vs 새로운 Board 반환**

- **고민:** 기물이 이동할 때 기존 `Board` 내부의 Map을 `put/remove`로 갱신하는 것이 직관적이다. 하지만 상태가 가변적이면 사이드 이펙트가 우려된다.

- **결정:** `Map.copyOf()`를 활용하여 기존 상태와 연결고리가 끊어진 불변 맵을 만들고, 이를 가진 새로운 Board 객체를 반환하도록 구현한다.

- **근거:** 가변 상태를 사용할 경우 부수효과(Side-effect)로 인해 예상치 못한 곳에서 데이터가 변경되는 버그가 발생하거나, 동시성 문제까지 신경 써야 하는 복잡성이 생긴다. 상태가 변할 때마다 기존 상태를 수정하는 대신 새로운 불변 상태를 생성하여 반환하도록 설계하면, 동작의 예측 가능성이 높아지고 이런 부작용에 대한 우려를 원천적으로 차단할 수 있다.

**3. 기물 객체의 라이프사이클: 매번 `new` 생성 vs 기물 인스턴스 캐싱 재사용**

- **고민:** 게임 초기화 시 32개의 기물을 배치할 때, `new Horse(Side.CHO)` 형태로 매번 인스턴스를 생성하는 것이 자원 낭비는 아닐까?

- **결정:** `PieceFactory`를 도입하여 기물 인스턴스를 캐싱하고 재사용한다.

- **근거:** 팀 규칙에 따라 기물은 자신의 '위치(Position)'를 상태로 갖지 않는 완벽한 불변 객체다. 즉, 보드판 위에 있는 2개의 '초나라 마'는 메모리 상에서 완전히 동일한 상태를 갖는다. 이를 싱글톤처럼 1개만 생성하여 공유함으로써 메모리를 절약한다.

**4. 다채로운 이동 규칙의 중복 제거: 하드코딩 vs 전략(Strategy) 패턴**

- **고민:** 기물 내부에 상, 하, 좌, 우 방향에 따라 `if`문과 `while`문이 산재해 있어 코드 중복이 매우 심하다. 이 반복적이고 고정적인 로직들을 어떻게 관리해야 재사용성과 응집도를 높일 수 있을까?

- **결정:** 상, 하, 좌, 우 등의 좌표 증감값을 `Direction` Enum으로 도출하고, 고정적인 공통 탐색 알고리즘을 `OneStepStrategy`, `SlideStrategy`, `JumpSlideStrategy`, `SequenceStrategy`로 추상화하여 기물에 주입한다.

- **근거:** 상하좌우 방향마다 고정되고 반복적으로 발생하는 탐색 로직(`if`, `while`)을 다형성으로 추상화하면 코드의 재사용성이 크게 향상된다. 기물은 '자신이 갈 수 있는 방향'이라는 순수 도메인 지식만 가지고, 실제 보드를 탐색하는 복잡한 절차는 전략 객체가 담당하게 역할을 분리함으로써, 규칙 변경이나 확장 시 해당 전략만 수정하면 되는 높은 응집도를 확보할 수 있다.

**5. 다형성의 활용: 상태 패턴(State) vs 전략 패턴(Strategy)의 분리 적용**

- **고민:** `if/else` 분기문을 제거하고 다형성을 활용해야 하는 상황이 많다. 기물마다 이동하는 규칙이 다르고, 플레이어의 턴(현재 턴, 대기 턴) 상태도 다르다. 이들을 구조가 비슷하다는 이유로 모두 동일한 디자인 패턴으로 묶어서 처리하는 것이 맞을까?

- **결정:** 런타임에 빈번하게 교체되는 플레이어의 턴 관리에는 상태 패턴(State Pattern)을 적용하고, 객체 생성 시 한 번 정해지면 변하지 않는 기물의 이동 규칙에는 전략 패턴(Strategy Pattern)을 적용하여 용도를 분리했다.

- **근거:** 두 패턴은 클래스 다이어그램 구조가 거의 동일하지만 설계의 '의도(Intent)'가 다르다. 턴 상태(`ActiveTurn`, `InactiveTurn`)는 게임 진행에 따라 매 턴마다 동적으로 상태가 교체되며 스스로 책임을 넘기는 행위가 중요하므로 상태 패턴이 적합하다. 반면, 기물의 이동 규칙(`OneStepStrategy`, `SlideStrategy`)은 기물 생성 시 알고리즘이 한 번 주입되면 게임이 끝날 때까지 변경될 일이 없으므로 전략 패턴이 부합한다. '상태 변경의 빈도'와 '의도'를 기준으로 패턴을 다르게 적용하여 객체지향적 설계의 목적을 코드에 명확히 드러냈다.

**6. 궁성(Palace) 도메인의 분리와 정적(Static) 캐싱**

- **고민:** 기물의 이동 시 보드에 존재하는 궁성의 대각선 규칙이 필요하다. `Board`가 `Palace`를 상태 인스턴스로 들고 있어야 할까? 기물의 `MovePattern` 상수에 궁성 방향을 추가해야 할까?
- **결정:** 궁성 데이터는 변하지 않는 기하학적 정보이므로, 정적 도메인(`Static Map` 또는 `Enum`)으로 분리하여 조회(Lookup) 방식으로 사용한다.
- **근거:** 장기판의 궁성 18개 점과 그에 따른 대각선 방향은 게임 내내 절대 변하지 않는 지형 데이터다. 이를 매번 새로 계산하거나 상태로 가질 필요가 없다. 또한, 기물의 이동 능력(`MovePattern`)은 위치에 독립적이어야 하므로, 위치에 종속적인 지형 정보인 `Palace`와 결합하면 단일 책임 원칙(SRP)을 위배하게 된다. 정적 도메인으로 분리함으로써 인스턴스 생성 비용을 없애고 구조를 명확히 했다.

**7. BoardReader의 공간 정보 제공 책임 확장 (Tell, Don't Ask)**

- **고민:** 궁성의 대각선 규칙을 이동 전략(Strategy)이 어떻게 알게 할 것인가? 전략 객체가 자신이 궁성 내부인지 판별(`inPalace`)하는 if 분기문을 갖는 것은 확장성에 좋지 않다.
- **결정:** 공간 정보의 전문가인 `BoardReader` 인터페이스에 `getPalaceDiagonals(Position)` 메서드를 추가하여 책임을 확장한다.
- **근거:** 기물이나 전략 객체가 상태를 캐묻지 않도록 `Tell, Don't Ask` 원칙을 적용했다. 기물은 단순히 보드에게 "여기서 갈 수 있는 대각선 방향을 알려줘"라고 요청하고, 보드는 정적 `Palace` 도메인을 조회하여 방향을 응답한다. 궁성이 아니면 빈 리스트를 반환하므로 전략 객체 내부의 if 분기문을 완전히 제거할 수 있었다.

**8. 기물의 행동 반경 제약(isWithinBoundary)과 전략(Strategy)의 역할 분리**

- **고민:** 궁과 사는 구궁 밖으로 나갈 수 없다. 이 제약을 이동 경로를 탐색하는 `MovementStrategy` 안에서 처리해야 할까?
- **결정:** 이동 전략은 길을 찾는 책임만 유지하고, 최종적인 행동 반경 제한은 `Piece` 클래스 내부(`isWithinBoundary`)에서 필터링하도록 역할을 분리했다.
- **근거:** `MovementStrategy`의 책임은 "어떻게 경로를 탐색할 것인가(How)"이다. 반면 궁성을 벗어날 수 없다는 것은 "이 기물은 어디까지 존재할 수 있는가(Who)"라는 기물 고유의 정체성이다. 제약을 기물 쪽으로 분리함으로써, 기본 `OneStepStrategy`를 수정하거나 궁성 전용 전략 클래스를 따로 만들 필요 없이 다형성과 응집도를 동시에 지킬 수 있었다.

**9. 데이터베이스 도입에 따른 Service 레이어의 필요성**

- **고민:** DB 연동 전에는 `ConsoleController`가 직접 `Game` 객체를 조작해도 기능상 문제가 없었다. DB(Repository)가 추가된 후에도 컨트롤러가 레포지토리를 직접 호출하는 것이 맞을까?
- **결정:** `GameService`라는 애플리케이션 서비스 계층을 새롭게 도입하여 흐름을 통제한다.
- **근거:** 컨트롤러의 본질적인 책임은 '입출력 제어'다. 영속성이 개입되면 "DB에서 게임을 꺼내오고(Load) -> 도메인 로직을 실행하고(Execute) -> 변경된 상태를 다시 DB에 넣는(Save)" 과정과, 이 모든 과정을 묶는 트랜잭션 경계 설정이 필요해진다. 이 복잡한 생명주기 조율 책임을 컨트롤러에 두면 단일 책임 원칙(SRP)이 위배되므로, 이를 전담할 서비스 레이어를 도입하여 도메인을 보호했다.

**10. 애그리거트 루트와 레포지토리의 1:1 매칭**

- **고민:** `game` 테이블과 `piece` 테이블 2개가 존재한다. 그렇다면 `GameRepository`와 `PieceRepository` 2개의 레포지토리가 필요할까?
- **결정:** 레포지토리는 오직 애그리거트 루트인 `GameRepository` 하나만 생성한다.
- **근거:** 하위 객체인 `Piece`가 독자적인 레포지토리를 통해 외부에서 직접 수정된다면, `Game` 객체는 자신의 장기판(`Board`) 위에서 기물이 움직였다는 사실을 모르게 되어 도메인의 정합성이 깨진다. 따라서 `gameRepository.save(game)` 단일 진입점만 열어두고, 내부적으로 `game`과 `piece` 테이블을 모두 다루도록 캡슐화하여 도메인의 무결성을 지켰다.

**11. 데이터베이스 테이블 설계의 제1원리 (What to Save)**

- **고민:** `Board`, `Player`, `Strategy` 등 수많은 객체 중 무엇을 테이블로 만들어야 할까?
- **결정:** 서버가 다운된 백지상태에서 게임을 완벽히 복구(Rehydrate)하는 데 필요한 최소한의 데이터인 `game`(메타데이터)과 `piece`(장기판 위 기물 상태) 2개의 테이블만 도출했다.
- **근거:** `Board`는 기물들을 감싸고 룰을 검증하는 캡슐일 뿐, 기물의 `x, y, side, type` 정보만 있으면 언제든 `new Board(...)`로 재창조할 수 있다. 영구적으로 기억해야 하는 핵심 상태값(엔티티)과 행위(메서드)를 분리하여 스키마를 구성했다.

**12. 도메인 로직과 DB 접근 로직의 완벽한 분리 (Repository와 DAO의 협력)**

- **고민:** DB 연동을 시작할 때 도메인 객체가 DB 테이블 구조를 직접 알게 되면 순수성이 깨진다. `game`과 `piece` 두 개의 테이블을 어떻게 객체지향적으로 관리해야 할까?
- **결정:** 도메인 계층에는 애그리거트 루트를 다루는 `GameRepository` 인터페이스만 둔다. 인프라 계층의 구현체인 `JdbcGameRepository` 내부에서 개별 테이블 쿼리를 전담하는 `GameDao`와 `PieceDao`를 조합하여 사용한다.
- **근거:** 레포지토리(Repository)는 '도메인' 관점에서 거대한 게임 전체를 저장하고 불러오는 책임(What)을 지고, DAO는 '인프라' 관점에서 특정 테이블에 쿼리를 날리는 책임(How)을 진다. 이렇게 역할을 나누면 도메인은 자신이 어떻게 저장되는지 전혀 모른 채 비즈니스 로직에만 집중할 수 있다.

**13. 영속성 저장 방식: 변경 감지(Update) vs 전체 갱신(Delete & Insert)**

- **고민:** 기물이 이동하거나 잡혔을 때, DB를 어떻게 업데이트해야 할까? 변경된 기물만 찾아 Update 쿼리를 날리는 것이 효율적일까?
- **결정:** 매 턴 저장이 일어날 때, 해당 게임의 기존 기물을 모두 삭제(`DELETE`)하고 현재 보드의 전체 상태를 스냅샷처럼 일괄 삽입(`BATCH INSERT`)한다.
- **근거:** 현재 도메인의 `Piece` 객체는 위치를 상태로 갖지 않는 공유된 불변 객체이며, DB 식별자(PK)를 갖고 있지 않다. 변경된 기물만 찾아내려면 식별자를 도메인에 억지로 추가하거나 복잡한 비교 로직을 작성해야 한다. 장기판의 기물은 최대 32개에 불과하므로, 복잡한 상태 추적을 포기하고 현재 상태를 통째로 덮어쓰는 것이 버그를 원천 차단하고 데이터 무결성을 보장하는 가장 단순하고 확실한 방법이다.

**14. 데이터 재조립(Rehydration)과 팩토리의 확장**

- **고민:** DB에서 `piece_type`과 `side` 같은 문자열 데이터를 읽어왔을 때, 이를 다시 객체로 변환하려면 레포지토리에 수많은 `switch` 분기문이 생겨야 한다.
- **결정:** 기존 `PieceFactory`에 `Map`과 함수형 인터페이스(`Function`)를 활용한 공통 생성 메서드(`create(PieceType, Side)`)를 추가하여 객체 복구 로직을 팩토리로 응집시킨다.
- **근거:** 객체 생성의 책임은 팩토리가 져야 한다. 인프라 계층(레포지토리)은 "어떤 기물을 만들지"에 대한 분기 지식을 가질 필요 없이, DB에서 읽은 값을 팩토리에 넘기기만 하면 된다. 이로써 레포지토리 코드는 간결해지고, 팩토리는 불변 객체 캐싱의 이점을 그대로 유지할 수 있다.

**15. if-else 처리**

- **고민:** 게임을 새로 시작할지, 기존 게임을 불러올지 분기하는 로직에서 흔히 발생하는 `if/else` 분기문 구조는 새로운 기능이 추가될 때마다 메인 컨트롤러 로직 수정을 강제한다. 또한 switch-case 금지, 함수형 인터페이스를 컨트롤러에 뒀을 때, 각각에 대해서 무엇이 우아한 방법인지 고민이 됐다.
- **결정:** `GameCommand` Enum을 정의하고 내부 속성으로 `Consumer<ConsoleController>`를 두어 각 명령(Command)과 구체적인 액션을 매핑해두며 새로운 시도를 해봤다.
- **근거:** 새로운 게임 모드가 추가되더라도 컨트롤러의 실행 코드(`gameCommand.execute(this)`)는 변경할 필요가 없을 것 같다.
- 다만 이러한 command 입력에 따른 분기는 switch-case가 개인적으로 가독성이 좋은 것 같다.

**16. 게임 상태 영속성 불일치 문제 (매 턴마다 새로운 게임이 생성되는 버그)**

- **고민:** 기물을 이동할 때마다 게임의 최신 상태를 DB에 반영하기 위해 `save()`를 호출했다. 하지만 기존 게임의 상태가 갱신되는 대신, 매 턴마다 새로운 게임 ID가 발급되며 `game` 테이블에 새로운 행(Row)이 무한정 삽입(Insert)되는 심각한 버그가 발생했다.
- **결정:** 영속성 관리 로직을 '생성(Create)'과 '수정(Update)'으로 명확히 분리했다. `GameDao`에 기존 상태를 갱신하는 `updateGame` 메서드를 추가하고, 최초 시작 시에만 `save(INSERT)`를, 이후 턴이 진행될 때는 발급된 게임 ID를 참조하여 `update(UPDATE)`를 호출하도록 흐름을 수정했다.
- **근거:** 게임은 한 번 생성된 후 내부 상태(현재 턴, 기물 위치)만 변하는 도메인이다. 상태가 변할 때마다 새로운 레코드를 생성하는 것은 데이터 무결성을 해치고 저장 공간을 낭비한다. 객체의 생명주기에 맞춰 갱신(Update) 로직을 분리하는 것이 구조적으로 적절하며, 이를 통해 "하나의 게임은 하나의 ID를 갖는다"는 당연한 원칙을 지킬 수 있었다.

**17. 트랜잭션 경계 설정과 커넥션 주입 (DAO의 안티 패턴 개선)**

- **고민:** 초기 코드에서는 기물 32개를 저장할 때 `PieceDao` 내부에서 매번 `DatabaseConnection.getConnection()`을 호출했다. 이로 인해 한 번의 저장에 30번 이상의 물리적 커넥션이 맺고 끊어져 성능이 극도로 저하되었다. 또한, 도중 에러가 발생해도 앞서 저장된 기물들을 롤백할 방법이 없어 데이터 부정합 위험이 컸다.
- **결정:** DAO 내부에서의 커넥션 직접 생성을 금지했다. 대신 상위 계층에서 커넥션을 생성하여 DAO 메서드의 매개변수로 주입(Injection)하도록 구조를 변경했다.
- **근거:** 게임 상태 갱신과 기물 목록 저장은 '전부 성공하거나 전부 실패'해야 하는 원자성(Atomicity)이 필수적이다. DAO가 커넥션을 직접 관리하면 여러 작업을 하나의 트랜잭션으로 묶을 수 없고 단일 책임 원칙(SRP)에도 위배된다. 커넥션 제어 책임을 외부로 넘김으로써 비로소 트랜잭션을 적용할 수 있는 기반을 마련했다.

**18. 트랜잭션 관리의 책임 주체 선정 (Service vs Repository)**

- **고민:** DAO에서 덜어낸 커넥션 관리와 트랜잭션 제어(`commit`/`rollback`) 책임을 어느 계층에 둘 것인지 고민했다. `GameService`가 커넥션을 직접 열고 닫게 되면, 순수해야 할 비즈니스 계층에 `java.sql.Connection`과 같은 특정 데이터베이스 인프라 기술이 강하게 결합(Coupling)되는 딜레마가 발생했다.
- **결정:** 서비스 계층의 객체지향적 순수성을 지키기 위해, JDBC 영속성을 전담하는 인프라 구현체인 `JdbcGameRepository`를 트랜잭션의 경계로 설정했다.
- **근거:** 비즈니스 로직(`GameService`)은 데이터베이스 기술이 JDBC인지, 파일인지 몰라야 한다. `JdbcGameRepository`의 통합 메서드(`save`, `update`) 내에서 단일 커넥션을 열고 여러 하위 DAO의 작업을 하나의 트랜잭션으로 묶어 처리함으로써, 서비스는 순수 도메인 로직 호출에만 집중할 수 있게 되어 관심사의 분리를 이뤄냈다.

**19. 대량 데이터 처리를 위한 배치 연산(Batch Insert) 도입**

- **고민:** 트랜잭션으로 묶어 단일 커넥션을 공유하게 되었음에도, 장기판 기물 최대 32개를 루프를 돌며 개별적인 `INSERT` 쿼리로 실행하면서 불필요한 네트워크 왕복 비용이 발생했다.
- **결정:** JDBC의 `addBatch()`와 `executeBatch()` 기능을 `PieceDao.insertPieces()`에 도입하여, 기물 데이터를 메모리에 모아두었다가 단 한 번의 네트워크 요청으로 일괄 처리하도록 구현했다.
- **근거:** 개별 쿼리는 매번 DB 엔진의 파싱과 네트워크 통신 과정을 거친다. 배치 연산을 활용하면 대량의 데이터를 한 번의 전송으로 처리할 수 있어 시스템의 DB I/O 오버헤드를 줄이고, 게임 저장 및 로드 시의 체감 속도를 높일 수 있었다.

**20. 테스트 병목 최적화 및 H2 DB 동시 접속 문제(File Lock) 해결**

- **고민:** 테스트마다 `@BeforeEach`에서 스키마 파일(`schema.sql`)을 읽고 테이블을 재생성(DROP/CREATE)하여 테스트 실행 시간이 늘어났다. 또한, 애플리케이션 실행 중 인텔리제이 DB 툴로 데이터를 확인하려고 하면 H2 DB 파일이 잠겨(`The file is locked`) 프로그램이 비정상 종료되는 문제가 잦았다.
- **결정:** 첫째, 스키마 생성 같은 무거운 작업은 `@BeforeAll`을 통해 클래스당 1회만 실행하고, 각 테스트 전에는 `DELETE FROM`으로 레코드만 가볍게 지우도록 최적화했다. 둘째, 테스트 환경은 디스크 I/O가 없는 인메모리 DB(`jdbc:h2:mem:testdb`)로 분리하고, 로컬 환경에는 `AUTO_SERVER=TRUE` 옵션을 주어 다중 접속을 허용 시도했다.
- **근거:** DDL(테이블 생성/삭제) 작업에 비해 DML(데이터 삭제) 작업이 빠르다. 물리 디스크 접근을 없앤 인메모리 환경은 TDD의 핵심인 피드백 루프를 단축시킨다.

## 사이클 2 첫 피드백 후 설계

### 고민

1. **기물 이동 (Soldier):** 궁성 내 전진 로직을 위해 부모(`Piece`)의 메서드를 오버라이딩하면서 OCP와 전략 패턴이 붕괴됨.
2. **턴 관리 (Turn):** `Game` 객체가 `Player`의 `TurnState`를 매번 묻고(Getter) 상태를 토글(Toggle)하는 절차지향적 코드가 발생함.
3. **플레이어 확장성 (Player):** 턴 관리를 빼버리면 행위가 없는 빈 껍데기가 되는데, 추후 확장성(방장, 전적 등)을 고려해 구조를 어떻게 가져갈 것인가.
4. **DB 효율성 (Piece 저장):** 매 턴마다 32개의 기물 위치를 전부 DELETE하고 INSERT하는 심각한 DB I/O 낭비가 발생함.
5. **트랜잭션 (Connection):** DAO와 Repository 계층에서 `Connection` 획득 방식이 파편화되어 하나의 트랜잭션으로 묶기 어려움.
6. **캡슐화 (Board):** DB 저장 및 DTO 변환을 위해 `Board` 내부 자료구조(`Map<Position, Piece>`)가 그대로 외부로 노출(Getter)됨.
7. **상태를 가진 서비스 (Stateful Service):** `GameService`가 `game`과 `currentGameId`를 필드로 가져 다중 사용자(싱글톤) 환경 시 치명적인 동시성 문제가 예상됨. 또한 서비스가 상태를 버릴 경우 세션(`gameId`) 관리 책임과 도메인 이벤트(이동 내역) 수집 책임을 누구에게 어떻게 분배할 것인지 모호함.

### 결정

1. 전진 전용 전략(`ForwardStepStrategy`) 도입
2. 상태 패턴(`State Pattern`) 설계 도입
3. 가벼워진 VO `Player(record)`와 일급 컬렉션 `Players(Map<Side, Player>)` 구축
4. 이벤트 소싱(Event Sourcing) 기반 이력(`MoveHistory`) 관리
5. Service가 통제하되 구조로 숨기기 (`ThreadLocal`, `Transaction Template`)
6. DTO 변환은 콜백 패턴(`forEachPiece`)으로, DB 저장은 이벤트 소싱으로 캡슐화 문제 해결
7. 무상태(Stateless) 서비스 전환 및 미커밋 이벤트(Uncommitted Events) 패턴 도입

### 근거

1. **상속 대신 조합(Composition):** 기물 객체의 순수성을 지키고, 필터링 로직을 전략 객체 내부로 밀어넣어 OCP를 준수함.
2. **Tell, Don't Ask (묻지 말고 시켜라):** `Game`은 분기문 없이 상태 객체에 행위를 위임하며, 상태 객체가 룰 검증과 다음 상태 전이를 원자적으로 처리해 사이드 이펙트를 차단함.
3. **일급 컬렉션과 SRP:** `Player`는 데이터를 담는 불변 객체(VO)로 역할을 한정하고, `Players`는 두 진영이 반드시 존재한다는 무결성 검증만 책임짐.
4. **객체-관계 패러다임 불일치 해소:** RDBMS의 진짜 불변성인 'APPEND ONLY(INSERT)'를 활용하여 디스크 I/O를 줄이고 도메인 식별자 오염을 방지함.
5. **비즈니스와 인프라의 격리:** Service는 트랜잭션 경계를 통제하면서도 JDBC 기술(`Connection`)에 종속되지 않게 됨.
6. **은닉화(Information Hiding):** 도메인(`Board`)은 외부 기술(DTO, DB)을 전혀 모른 채 자신이 가진 데이터에 행동을 적용하기만 하므로 내부 구조 변경에 완벽히 닫혀있음.
7. **스레드 안전성 및 도메인 이벤트 응집력 강화:** 서비스 필드에서 상태를 제거해 다중 사용자 환경의 동시성 문제를 차단하고, 세션(`gameId`) 책임은 클라이언트 역할인 `ConsoleController`로 분리함. 또한 발생한 이벤트(이력)를 애그리거트 루트(`Game`)가 임시 보관(`List<MoveEvent>`)하고 레포지토리가 수거하도록 설계하여, 서비스 계층이 도메인 내부의 복잡한 파급 효과(기물 포획, 외통수 등)를 일일이 파악해 DB에 꽂아넣는 절차지향적 책임을 지지 않도록 도메인과 인프라를 격리함.
