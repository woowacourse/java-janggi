# 2.1단계 - 기물의 확장

- 사이클1에서 제외했던 궁성(宮城) 영역의 규칙을 포함하여 기물의 이동을 구현한다.
- 장기는 왕이 잡히는 경우 게임에서 진다. 왕이 잡혔을 때 게임을 종료해야 한다.
- 현재 남아 있는 기물에 대한 점수를 구할 수 있어야 한다.
- 점수 계산 규칙은 직접 요구사항을 분석하여 정의한다.

### 왜 궁성을 따로 봐야 하지?

- 장기판 전체가 같은 규칙으로 움직이는 게 아니라, 궁성이라는 특수한 영역에서는 일부 기물의 이동 규칙이 달라지기 때문.
- 궁성 내부인지 궁성 대각선 경로가 존재하는지를 판단해야 하는 특수 규칙 영역이라고 볼 수 있기 때문에

### Board가 다 처리하면 되지 않나?

Board가 장기판 전체 상태와 이동 경로 계산, 궁성 특수 규칙까지 모두 알게 되면 책임이 너무 커질 수 있음.

### 그렇다면 궁성만 따로 객체로 분리하는 게 낫지 않나?

궁성은 일반 보드와는 다른 별도의 규칙 집합이므로, Palace 같은 객체로 분리하면 특수 영역 규칙을 더 명확하게 드러낼 수 있음.

### 그렇다면 궁성에서 진짜 중요한 건 뭐지?

궁성은 단순한 좌표 범위가 아니라, 특정 기물이 일반 규칙과 다르게 움직이게 만드는 특수 영역이라는 점이 중요.

### 게임 종료에서 장군, 외통수까지 다 구현해야 하는가?

현재 단계에서는 요구사항을 너무 넓히지 않고, “왕이 실제로 잡히는 경우 종료”로 좁혀 해석하는 것이 적절하다고 생각함.

### 게임 종료 상태를 어디서 관리해야 하지?

게임 전체의 상태 변화이므로 Game이 종료 여부를 알고 있어야 함.

### 게임 종료를 구현하려면 무엇이 필요하지?

말 이동 이후 잡힌 기물이 있는지 알아야 하고, 그 기물이 왕인지 확인할 수 있어야 함.

## 설계 관점

### 그렇다면 궁성은 무엇을 책임져야 하는가?

- 궁성 내부 좌표 여부 판단
- 궁성 내부 대각선 경로 여부 판단

### Board는 무엇을 해야 하는가?

- 일반 직선 경로와 궁성 대각선 경로 중 어떤 규칙을 적용할지 조합
- 기물 전략이 궁성 관련 정보를 질의할 수 있도록 제공

### 왜 Palace를 따로 두는가?

- 궁성 규칙이 Board에 섞이지 않게 하기 위해
- 특수 영역 규칙을 한 곳에 모으기 위해
- 궁성 규칙을 코드 상에서 더 명확히 드러내기 위해

### 게임 종료를 예외로 하면?

- 게임 종료는 예외 상황으로 보기 어려움
- 따라서 GameOverException과 같은 것은 기각!

### 그렇다면 도메인 객체의 변경을 최소화 하며 DB를 적용해야 하는 이유는?

- 도메인이 DB에 강하게 결합되어 있다면, 저장 방식이 바뀌는 경우에는 게임 로직 자체가 문제가 생길 수 있음
- 도메인은 장기 게임 자체를 표현해야하지, 저장 방식에 대해서는 책임지면 역할이 섞임
- 추가 기능 때문에 본질적인 게임 도메인이 바뀌면 안 됨.

### 도메인 객체를 최소화하려면 DB를 어떻게 붙여야하지?

- 도메인이 DB를 알면 안 되지 않나?
    - 도메인은 DB를 알지 못하게 하자.
    - 그렇다면 DB에 저장할 때 필요한 정보만을 객체로 감싸서 전달해주면 되겠다.
- Repository와 같은 저장소 계층이 필요할까?
    - 도메인과 DB를 분리하려면 하는 게 적절한 것 같음.
- DB와 도메인을 분리해야하나?
    - GameRepository (interface)
    - JdbcGameRepository(implement)
- 변환은 어디서 해야하지?
    - 따로 GameMapper에서 해주면 좋지 않을까?
    - 도메인과 DB사이의 데이터 변환을 해주는 것을 명확하게 보여줄 수 있을 것!

### 동작 과정 생각하기

#### save(game):

1. game테이블에 턴, 종료여부를 저장
2. 해당 게임의 기물 정보들(camp, 타입, 위치)을 piece 테이블에 저장

기존 piece 데이터는 전부 지우고 현재 보드 상태를 다시 insert

#### findInProgressGame():

1. game 테이블에서 finished = false인 게임 1개를 조회한다.
2. 그 게임의 id를 얻는다.
3. piece 테이블에서 game_id에 해당하는 기물들을 전부 조회한다.
4. 기물 목록으로 Board를 만든다.
5. current_turn과 함께 Game.of(board, currentTurn)으로 게임을 복원한다.

그렇다면 결국 보드의 상태를 읽어와야함. 어떻게 읽어올까?
-> 도메인 수정을 최소화니까 필요한 정보만 뽑아올 객체를 만들자.

# 고민한 부분

1. Game 생성자

- TDD를 진행하면서 Game의 생성자를 수정해야 할 일이 생겼음. 게임이 종료되었는지 확인을 위해서는 따로 테스트에 테스트 종료를 위한 보드를 주입해줘야 했는데, 기존의 Game 생성자에서는 그러한 로직이
  존재하지 않았음.
- 따라서 private 생성자와 this를 통해서 기존의 생성자를 수정하고, 게임 중간에 대한 정보를 통해서 Game객체를 만들 수 있도록 정적 펙토리 메서드를 만들었음.
- 이런식으로 하면 다른 개발자가 따로 of()를 통해서 게임을 생성하려고 할 수도 있지 않을까 하는 생각을 하게 되었음. 이러한 경우는 어떻게 해야하는걸까?

생각을 해봤던 건 Game을 만드는 경로가 두 개인데, 이를 도메인적으로

- 새 게임 시작과
- 진행 중 상태로부터 게임을 복원

이렇게 두 가지로 생각을 해보았음.
근데 다른 개발자가 처음 보았을 때 "이거 아무렇게나 만들어도 되는건가? 이거 어떻게 써야하지?" 라는 오해를 할 수 있지 않을까?? 하는 생각을 하게 됨.

2. 게임 종료 로직 구현을 위한 보드에서 잡힌 기물 즉, Optional<Piece>를 반환

- 게임 종료를 구현하려면 왕이 잡혔는지 판단할 수 있어야 했다.
- 따라서 매 턴 기물의 이동 이후, 이동 결과로 잡힌 기물이 있는지 확인하고 해당 기물이 왕이라면 게임을 종료 상태로 변경하도록 구현하였다.
- 이때 이동 결과를 Optional<Piece>로 표현할지, 아니면 의미를 더 명확히 드러내는 MoveResult 객체로 감쌀지 고민이 생김.
- 개인적으로 게임 종료에 대한 판단과 관련되어있어 MoveResult가 자연스럽지 않을까?
- 하지만, 한 편으로는 지금 단계에서 단순 데이터를 감싼 객체가 되어 복잡도만 높이는거 아닌가? 싶기도 함.

3. 테스트코드에서 데이터를 저장하고 조회할 때 디미터의 법칙

- Repository 테스트를 작성하면서 디미터 법칙을 어기게 되는 것을 볼 수 있었음
- savedGame.board().findBy(...).type() 와 같이 사용중.
- 내부 상태를 검증하기 위해서는 동등성 비교를 해야하는데, 도메인객체의 수정을 최소한으로 하고싶음.
- 따로 Game이나 Board에서 Hashcode or equals를 오버라이딩 해서 처리해야하는지 아니면 현재 방향으로 충분한지 고민됨.

# 장군 & 외통수 구현하기

## 장군이란 무엇인가?

- 장군이란 현재 보드판에서 장군이 다음턴에 공격 가능한 상태
- 어떤 기물이 장군의 위치로 합법적으로 이동할 수 있다면 장군

## 누가 장군을 판단해야 하는가?

- Board는 기물 배치 상태를 가진다.
- Piece는 자신의 이동 규칙을 안다.
- Game은 턴 진행과 이동 절차를 조율한다.
- 장군 판정은 여러 객체의 정보를 함께 사용하므로 별도의 판정 객체가 담당한다. (ThreatAnalyzer객체)

## 장군은 어떻게 판단할 수 있을까?

- 장군의 위치를 찾는다.
- 찾은 장군의 상대편의 기물들을 순회해서 Set 구조에 가능한 위치를 담는다.
- 가능한 구조에 장군이 있다면 장군 처리를 한다.

## 외통수는 어떻게 판단할 수 있을까?

- 가능 수: 기물의 행마 규칙상 둘 수 있는 수
- 합법 수: 가능한 수이면서, 둔 뒤에도 자기 장군이 공격당하지 않는 상태
- 외통수: 현재 장군 상태이고, 그런 합법 수가 하나도 없는 상태
  - 장군 && !합법 수

=> 합법수에 대한 정의만 내리면 외통수를 구현할 수 있음.
