## **구현할 기능 목록**

### 입력 기능

- [x] 상차림을 입력받는다.
    - [x] [예외상황] 해당하지 않는 상차림을 입력한 경우, "[ERROR] 존재하지 않는 상차림입니다."를 출력하고 재입력 받는다.

- [x] 움직일 기물의 좌표를 입력받는다.
    - [x] [예외상황] 좌표 형식이 잘못된 경우, "[ERROR] 잘못된 좌표 형식입니다."를 출력하고 재입력 받는다.
    - [x] [예외상황] 좌표가 2개가 아닌 경우, "[ERROR] 좌표는 2개만 입력해 주세요."를 출력하고 재입력 받는다.
    - [x] [예외상황] x좌표와 y좌표의 범위가 잘못된 경우, "[ERROR] x좌표와 y좌표의 범위가 올바르지 않습니다."를 출력하고 재입력 받는다.
    - [x] [예외상황] 해당 좌표에 기물이 존재하지 않는 경우, "[ERROR] 해당 좌표에 기물이 존재하지 않습니다."를 출력하고 재입력 받는다.
    - [x] [예외상황] 해당 좌표의 기물이 나의 기물이 아닌 경우, "[ERROR] 본인 진영의 기물이 아닙니다."를 출력하고 재입력 받는다.

- [x] 움직이고 싶은 위치의 좌표를 입력받는다.
    - [x] [예외상황] 좌표 형식이 잘못된 경우, "[ERROR] 잘못된 좌표 형식입니다."를 출력하고 재입력 받는다.
    - [x] [예외상황] 좌표가 2개가 아닌 경우, "[ERROR] 좌표는 2개만 입력해 주세요."를 출력하고 재입력 받는다.
    - [x] [예외상황] x좌표와 y좌표의 범위가 잘못된 경우, "[ERROR] x좌표와 y좌표의 범위가 올바르지 않습니다."를 출력하고 재입력 받는다.
    - [x] [예외상황] 움직일 기물의 좌표와 움직이고 싶은 좌표가 같은 경우, "[ERROR] 움직일 기물의 좌표와 움직이고 싶은 좌표는 달라야 합니다."를 출력하고 재입력 받는다.
    - [x] [예외상황] 해당 좌표에 이동할 수 없는 경우, 움직일 기물의 좌표부터 재입력 받는다.

### 보드 초기화 기능

- [x] 상차림 기능
    - [x] 왼상 차림 - 상마상마
    - [x] 오른상 차림 - 마상마상
    - [x] 안상 차림 - 마상상마
    - [x] 바깥상 차림 - 상마마상
- [x] 게임 시작 시 장기판과 전체 기물을 올바른 위치에 초기화한다.
    - [x] 각 플레이어가 선택한 상차림에 맞게 보드를 초기화한다.

### 기물 이동 경로 계산 기능

- [x] 기물의 출발지부터 도착지까지의 경로를 계산한다.

### 기물 이동 기능

- [x] 각 기물은 이동 규칙에 맞게 이동한다.
    - [x] 졸・병(卒·兵) - 좌, 우, 앞으로 이동
    - [x] 사(士) - 궁성 내부에서 1칸씩 이동(선따라 이동)
    - [x] 상(象) - 1칸 이동 후, 대각선 2칸
    - [x] 마(馬) - 1칸 이동 후, 대각선 1칸
    - [x] 포(包) - 기물을 이용해 뛰어넘어 이동 (포끼리는 뛰어 넘지도 먹지도 못함)
    - [x] 차(車) - 앞, 뒤, 좌, 우 직선으로 원하는 곳까지 이동 가능
    - [x] 궁(漢·楚) - 궁성 내부에서 1칸씩 이동(선따라 이동)

### 궁성 기능

- [x] 궁성 영역은 아래와 같다.
    - [x] 초나라의 궁성 영역은 x좌표(3~5), y좌표(0~2)이다.
    - [x] 한나라의 궁성 영역은 x좌표(3~5), y좌표(7~9)이다.

- [x] 각 기물의 궁성에 대한 규칙을 적용한다.

### 게임 종료 기능

- [x] 상대편 궁을 먼저 잡은 나라가 승리한다.

### 점수 계산 기능

- [x] 상대편 기물을 잡으면, 해당 기물에 해당하는 점수만큼 점수를 얻을 수 있다.
    - [x] 얻은 점수는 자신의 점수에서 차감한다.
    - [x] 초나라의 초기 점수는 72.0점, 한나라의 초기 점수는 73.5점이다.
    - [x] 각 기물의 점수: 졸·병(2), 사(3), 상(3), 마(5), 포(7), 차(13)

### DB 저장 기능

- [x] 보드판의 현재 상태를 저장한다.

- [x] 게임의 이전 기록이 존재하면, 사용자는 이어서 게임을 진행할 수 있다.

### 출력 기능

- [x] 현재 차례를 출력한다.

- [x] 장기판을 출력한다.
    - [x] 보드판은 고정되어 있기 때문에, 한나라의 초기 상차림만 반대로 한다.

- [x] 승리 여부를 출력한다.

- [x] 초나라와 한나라의 현재 점수를 출력한다.

## **프로그래밍 요구 사항**

- [x] 자바 코드 컨벤션을 지키면서 프로그래밍한다.
    - [x] 기본적으로 Java Style Guide을 원칙으로 한다.
- [x] indent(인덴트, 들여쓰기) depth를 2를 넘지 않도록 구현한다. 1까지만 허용한다.
    - [x] 예를 들어 while문 안에 if문이 있으면 들여쓰기는 2이다.
    - [x] 힌트: indent(인덴트, 들여쓰기) depth를 줄이는 좋은 방법은 함수(또는 메서드)를 분리하면 된다.
- [x] 3항 연산자를 쓰지 않는다.
- [x] else 예약어를 쓰지 않는다.
    - [x] else 예약어를 쓰지 말라고 하니 switch/case로 구현하는 경우가 있는데 switch/case도 허용하지 않는다.
    - [x] 힌트: if문에서 값을 반환하는 방식으로 구현하면 else 예약어를 사용하지 않아도 된다.
- [x] 모든 기능을 TDD로 구현해 단위 테스트가 존재해야 한다. 단, UI(System.out, System.in) 로직은 제외
    - [x] 핵심 로직을 구현하는 코드와 UI를 담당하는 로직을 구분한다.
    - [x] UI 로직을 InputView, ResultView와 같은 클래스를 추가해 분리한다.
- [x] 함수(또는 메서드)의 길이가 10라인을 넘어가지 않도록 구현한다.
    - [x] 함수(또는 메소드)가 한 가지 일만 하도록 최대한 작게 만들어라.
- [x] 배열 대신 컬렉션을 사용한다.
- [x] 모든 원시 값과 문자열을 포장한다.
- [x] 줄여 쓰지 않는다(축약 금지).
- [x] 일급 컬렉션을 쓴다.
- [ ] 모든 엔티티를 작게 유지한다.
- [ ] 3개 이상의 인스턴스 변수를 가진 클래스를 쓰지 않는다.

## **미션 중 기록**

### 사이클 1

- 상태 위치를 결정할 때 고민한 순간 1회
    - 기물의 위치 정보를 누가 관리해야 할지 고민했습니다.
      처음에는 기물이 자신의 위치를 직접 관리하는 것이 자율적이라고 생각했지만,
      기물이 이동할 때마다 보드와 동기화를 맞춰야 하는 문제가 발생한다는 것을 깨달았습니다.
      상태는 함께 변경되어야 하는 객체가 관리하는 것이 자연스럽다고 판단하여,
      Piece를 가지고 있는 State를 Board가 관리하도록 결정했습니다.
- 불변/캡슐화를 적용한 코드 1곳
    - 특정 기물의 좌표를 관리하는 Position의 내부 필드를 final로 선언하여 외부에서 변경되지 않도록 했습니다.
      이를 통해 기물 이동 시 예상치 못한 좌표 변경을 방지하고, 로직이 예상대로 동작하는 영역을 확보할 수 있었습니다.
- 규칙 적용으로 변경한 설계 1곳
    - 초기 설계에서는 기물의 이동 규칙을 하나의 메서드 안에서 기물 종류별로 분기 처리하려 했습니다.
      하지만 [조건문 대체 기준]과 [책임 분리 규칙]을 적용하여, 공통된 행위를 가진 기물들을 하나의 범주로 묶고
      각 기물이 자신의 이동 규칙을 스스로 검증하도록 구조를 변경했습니다.
- 조건문을 다형성으로 대체한 코드 1곳
    - 기물 이동 시 기물 종류마다 이동 가능 여부를 판단하는 로직을 조건문으로 작성하면 최소 7개, 최대 14개의 조건문이 필요했습니다.
      이를 각 기물 클래스가 validateDirections()를 오버라이딩하여 자신의 이동 규칙을 스스로 판단하도록 변경했습니다.
      특정 기물의 이동 규칙을 수정할 때 해당 클래스만 변경하면 되므로 변경 범위가 줄어든 점이 좋았습니다.
- 인터페이스/추상 클래스를 도입한 이유
    - Piece를 추상 클래스로 도입한 이유는 모든 기물이 공통으로 가져야 할 PieceInfo와
      validateDirections() 메서드를 상위 클래스에서 정의하여 중복을 줄이기 위해서입니다.
      또한 Board가 기물의 종류를 알 필요 없이 validateDirections()만 호출하면 되도록 하여,
      기물 추가 시 보드 코드를 수정하지 않아도 되는 구조를 만들기 위해서입니다.
- 새 기물 추가 시 변경 범위 테스트 (가상으로)
    - 새로운 기물 "용"을 추가한다고 가정하면, PieceType enum에 DRAGON을 추가하고,
      Piece를 상속받는 Dragon 클래스를 생성하여 validateDirections()를 구현한 뒤,
      InitialPosition 또는 Board의 초기화 로직에 용의 초기 위치를 추가하면 됩니다.
      기존의 다른 기물 클래스나 Board의 이동 로직은 수정하지 않아도 되므로,
      다형성을 적용하기 전과 비교해 변경 범위가 명확하게 줄어든 것을 확인할 수 있습니다.

### 사이클 2

### 기능 추가로 인해 수정한 위치 개수

- 궁성 영역 추가 시 -> Position, SingleMovingPiece, StraightMovingPiece, Soldier 수정
- DB 연동 추가 시 -> Board에 `load()` 정적 팩토리 메서드 추가, BoardInitializer에 `fillEmptyPositions()` 추출, Game 도메인 추가,
  Controller/Service 계층 추가

### 사이클1 때보다 수정 범위가 줄었는가/늘었는가

- 궁성 영역 구현 시 기물 클래스 계층 구조를 재정의하면서 수정 범위가 사이클 1보다 늘어났습니다. 다만 `validateDirectionsInPalace()`를 부모 클래스에서 정의하고 자식 클래스에서
  오버라이딩하는 구조 덕분에, 각 기물의 궁성 규칙이 해당 클래스 안에서만 변경되어 다른 기물에 영향을 주지 않았습니다.

### 도메인과 저장소를 분리한 코드 1곳

- Board 도메인은 게임 상태를 `Map<Position, State>`로 관리하고, DB 저장 및 조회는 BoardRepository가 담당합니다.
  `Board.load(Map<Position, PieceInfo>)`를 통해 DB에서 조회한 데이터를 도메인 객체로 복원하는 방식으로 도메인이 DB에 직접 의존하지 않도록 했습니다.

### DB 변경 시 도메인 코드 영향 분석

- H2에서 MySQL로 DB를 변경해도 `BoardRepositoryImpl`과 `GameRepositoryImpl`의 SQL 쿼리만 수정하면 된다고 생각합니다. Board, Game 등 도메인 객체는
  변경이 필요하지 않습니다. 다만, `GameRepositoryImpl.findLatest()`의 `LIMIT 1`이 포함된 쿼리는 수정이 필요할 것 같습니다.

### 규칙 적용으로 변경한 코드 1곳

- `Piece.validateClearPath()`에 Board를 직접 넘기던 양방향 의존을 제거했습니다. Board에서 경로 중간 기물 정보만 추출해 `Map<Position, PieceType>`으로
  전달하고, 목적지 타입을 `PieceType destinationPieceType`으로 별도 전달하는 방식으로 변경했습니다. 이를 통해 Piece가 Board를 알지 않아도 경로 검증이 가능해졌습니다.
