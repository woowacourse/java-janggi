## 미션 중 기록

**상태 위치를 결정할 때 고민한 순간 1회**  
기물의 이름을 기물이 갖고 있어야하는지에 대한 고민이 있었습니다.
기물은 자신이 어떤 기물이지 알려줘야할 의무가 있다고 생각했고, 이름을 표현하는 상태를 가지도록 설계하려 하였으나,
단순히 자신이 어떤 기물인지 알려주기 위해 상태까지 가져야 하는가에 대한 의문이 들어 고민되었던 것 같습니다.
결과적으로 단순히 이름을 알려주는 행동을 위해 필드는 필요 없다고 판단하였습니다.

**불변/캡슐화를 적용한 코드 1곳**   
Position을 불변으로 작성하였습니다.
생성 후 내부 상태가 변하지 않고, 동등성 비교도 값 기반으로 안전하게 동작한다고 생각합니다.
또한 좌표와 관련된 계산을 Position내부에서 수행하므로써 캡슐화를 지키려고 노력했습니다.

**규칙 적용으로 변경한 설계 1곳**
> 규칙 7. 테스트와 설계의 관계 규칙  
> 데이터를 꺼내지 말고, 객체에게 직접 물어본다. (Tell, Don't Ask)   
> (If-Then)   
> \- 데이터를 직접 꺼내어 연산하고 있다면 → 데이터를 가진 객체에게 직접 물어보도록 수정하여 변경 여파를 내부에 가둔다.   
> \- 테스트가 깨지면 → 테스트가 아니라 설계를 수정한다.

도착 좌표의 객체가 같은 팀이면 이동할 수 없다라는 규칙을 구현하며 막혔었습니다.
팀 상태(정보)는 기물이 가지고 있고 두 기물의 팀을 비교해야 하는데, 밖에서 꺼내는 방법은 캡슐화 위반이라고 느껴졌습니다.
이동하려는 기물에게 도착 좌표의 기물이 같은 팀인지 확인하라고 물어보는 방법을 고려하게 되었고,
두 기물들이 서로 협력하며 외부로 팀 정보를 노출하지 않고 판정할 수 있는 방법을 적용하게 되었습니다.  
리팩터링을 진행하며 getter의 정의에 대해 다시 한 번 생각해보고, getter를 사용하여 캡슐화를 저해하지 않고 자연스럽게 사용하는 기준을
찾은 것 같습니다. 결국 enum으로 정의된 Team 정보를 가져와 직접 비교하는 방식으로 변경하였습니다.

**조건문을 다형성으로 대체한 코드 1곳**    
처음 설계때 부터 기물들이 자신의 이동 규칙을 자율적으로 내포하고 있고,
같은 요청을 받고 응답할 수 있다고 판단하여 다형성으로 설계하였습니다.
그 외에 보드 초기화 부분에 아직 복잡한 조건문들이 자리하고 있어 대체가 필요하다고 느낍니다.

**인터페이스/추상 클래스를 도입한 이유**    
기물 인터페이스를 도입하였는데,
각 기물들에 대하여 공통된 필드나 기본적으로 수행해야할 행동이 없다고 판단하여 인터페이스를 선택하게 되었습니다.  
인터페이스를 적용하여 구현을 완료한 뒤, 공통 필드나 메서드는 추상 클래스 레이어를 추가하여 중복을 제거하였습니다.

**새 기물 추가 시 변경 범위 테스트 (가상으로)**  
새 기물 추가 시, 새로운 배치 전략과 새 기물 클래스만 추가되면 된다고 생각합니다.
기존 기물들과 궤를 달리하는 기물이라면 수정이 대폭 필요할 것 같다고 느낍니다.

책임 분리에 매몰되어 메서드나 인스턴스를 만들었다 지웠다 한 것을 제외하면 기능을 위한 수정만 있었습니다.
핵심 도메인(기물, 보드)은 특히 구조가 괜찮다고 느낄 수 있었습니다.
하지만 게임 흐름쪽(컨트롤러, 게임) 부분이 빈약한 구조라고 느꼈습니다.
수정 범위를 줄이는 대신 GameRepository가 흐름에 맞춰 설계되어
구체적이고 세분화된 행동을 하게되고, 코드가 길어지고 사용이 어려워진 것 같습니다.

**도메인과 저장소를 분리한 코드 1곳**

GameRepository가 DB 구현 세부사항을 전부 감추도록 하였습니다.
JanggiGame은 repository.movePiece(), repository.createGame()과 같은 메서드만 호출할 뿐 어떤 DB를 사용하는지, 어떤 쿼리를 보내는지 모릅니다.
SQLException도 GameRepository 안에서 RuntimeException으로 감싸서, 도메인 쪽으로 checked exception이 전파되지 않게 처리했습니다.
---
JanggiService를 도입하여 Game에서 repository 의존성을 완전히 끊어냈습니다.

**DB 변경 시 도메인 코드 영향 분석**

JDBC는 DB 종류에 상관없이 동일한 인터페이스를 제공하므로, H2에서 MySQL로 바꿔도 DBConnection의 URL만 변경하면 됩니다.
현재 코드에서는 표준 SQL만 쓰고 있어서 Repository 수정 없이 연결 정보 변경만으로 DB 교체가 가능하다고 생각합니다.
즉, GameRepository 내부의 SQL이나 도메인 코드는 수정할 필요 없을 것 같습니다.
결국 도메인 객체(Game, Board, Piece 등)는 DB가 뭔지 아예 모르니까 어떤 DB를 쓰든 영향이 없습니다.
만약 Repository를 인터페이스로 추상화하면 JDBC가 아닌 다른 저장 방식(파일, 메모리 등)으로 바꿀 때도
구현체만 갈아끼우면 되기 때문에 도메인 변경 없이 대응이 가능하고 테스트를 용이하게 만들 수 있을 것 같습니다.

**규칙 적용으로 변경한 코드 1곳**
> 15. 저장 경계 규칙  
      > Service 계층 객체 이외의 객체들은 Repository를 몰라야한다.

현재 Service 계층인 JanggiGame만 GameRepository를 알고 있습니다.
JanggiController는 JanggiGame에게 요청할 뿐 GameRepository의 존재를 모르고,
Board, Piece 같은 도메인 객체들도 GameRepository를 모르도록 하였습니다.
DB 접근이 필요한 모든 작업은 JanggiGame을 통해서만 일어나게 됩니다.
다만 현재 구조에서 아쉬운 점은, GameRepository가 인터페이스가 아니라 구현체에 직접 의존하고 있어
JanggiGame의 테스트 코드 작성이 어려운 상태입니다.
---
JanggiService가 GameRepository 인터페이스를 알고 있도록 변경하였고, JanggiGame은 순수 도메인 객체로 분리하였습니다.
GameRepository를 인터페이스로 추상화했고, FakeGameRepository를 활용하여 JanggiService도 쉽게 테스트할 수 있었습니다.
