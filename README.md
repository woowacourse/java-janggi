* 상태를 객체로 모델링하고 이유를 설명할 수 있다.
    * 상태란?
    * 모델링하는 이유:
    * 장점:
    * 단점:
* 조건문 대신 다형성을 적용할 수 있다.

2. commit 단위에 대한 논의가 이뤄지고, 규칙을 만들어보자.
    * feat: 커밋명
    * 커밋명은 한국어로 하되, AI에게 구체적인 컨텍스트를 주입시켜 만든다.
    * 커밋의 단위는 TDD하면서 테스트 성공하면 그것을 하나의 단위로 (기능 단위)

3. 페어 프로그래밍의 로테이션의 기준을 명확히 하는 것 어떨까?
    * 기능 단위로 하되, 상대가 완벽하게 납득할 때까지 설명하고 키보드를 잡는다.

4. 테스트를 어떤식으로 작성하면 좋을지 통일해보자. → 테스트 작성 가이드 작성해보자.
    * 테스트는 메서드 단위로 하되, 한 가지 역할만 담당한다.
    * `@DisplayName()` 사용하기
    * DisplayName의 이름은 “조건 + 행동 + 기대결과” 구조
    * 테스트 메서드 이름은 영어로 작성하고, 위 구조를 따른다.

5. 어디까지 설계할것인지를 정해보자.
    * 사용자 요구사항설계
    * 기능 요구사항 설계

# 요구사항 정리

### 사용자 요구사항

- 플레이어 1은 초나라, 플레이어 2는 한나라이다.
- 사용자는 장기의 네 가지 상차림에 대해서 선택한다.
    - 상마마상/마상상마/상마상마/마상마상
    - 왼상차림(상마상마) `LEFT_ELEPHANT`
    - 오른상차림(마상마상) `RIGHT_ELEPHANT`
    - 안상차림(마상상마) `INNER_ELEPHANT`
    - 바깥상차림(상마마상) `OUTER_ELEPHANT`
- 사용자는 턴을 넘기거나, 기물을 움직일 수 있다.
