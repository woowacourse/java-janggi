## 1.2단계 - 기물 이동

- 2단계에서는 기물 이동 구현이 목적이니까 종료는 `Ctrl+C`로 강제 종료한다.

### 잘못된 기물 선택 시나리오

1. 다른 나라의 기물을 선택했을 때
    1. 예외: 다른나라의 기물 선택
    2. `[ERROR] 다른 나라의 기물을 선택할 수 없습니다.`
2. 기물이 없는 곳을 선택했다. (빈칸 or 장기판 외부)
    1. 예외: 기물이 없는 곳을 선택
    2. `[ERROR] 현재 위치에 존재하는 기물이 없습니다.`

### 기물 이동 규칙

- 궁성 영역 - 고려하지 않는다. (사이클 2)
- 기물 이동 규칙 공통
    - 현재 위치로 이동할 수 없다.
    - 보드 영역 밖으로 이동할 수 없다.
    - 목적지에 아군이 있으면 이동할 수 없다.
    - 목적지에 적군이 있으면 잡아낸다.

- `차`: 4방위로 이동한다.
    - 목적지까지의 경로에 기물이 있으면 이동할 수 없다.
- `포`: 4방위로 이동한다.
    - 무조건 목적지까지의 경로에 포를 제외한 기물이 하나만 존재해야 한다.
- `마`: 4방위 중 한 방향으로 한 칸 이동하고 대각선의 한 방향으로 1칸 이동해야 한다.
    - 목적지까지의 경로에 기물이 있으면 이동할 수 없다.
- `상`: 4방위 중 한 방향으로 한 칸 이동하고 대각선의 한 방향으로 2칸 이동해야 한다.
    - 목적지까지의 경로에 기물이 있으면 이동할 수 없다.
- `졸`: 직진과 좌, 우로만 한 칸 이동해야 한다.
    - 한 칸이라서 경로에 기물이 있을 리가 없다.
- `사, 장`: 궁성 내부에서 한칸씩 움직인다.

# 2.1단계 - 궁성, 승리 판정, 기물별 점수

## 궁성

### 궁성 영역

![궁성](/images/궁성-위치.png)

- 한나라 궁성: `(0,3)` ~ `(2,5)`
- 초나라 궁성: `(7,3)` ~ `(9,5)`
- 궁성 내부에는 대각선이 존재한다.

### 궁성 내 기물 이동 규칙

- `장(將)`: 궁성 내에서만 이동할 수 있다.
    - 가로, 세로, 대각선 방향으로 한 칸 이동할 수 있다.
    - 단, 대각선 이동은 궁성의 대각선 위에 있을 때만 가능하다.
- `사(士)`: 궁성 내에서만 이동할 수 있다.
    - 장과 동일한 이동 규칙을 따른다.
- `차(車)`: 궁성 내 대각선을 따라 이동할 수 있다.
    - 궁성 밖에서는 기존 4방위 직선 이동만 가능하다.
- `포(包)`: 궁성 내 대각선을 따라 이동할 수 있다.
    - 기존 규칙과 동일하게 기물 하나를 반드시 넘어야 한다.
- `졸/병(卒/兵)`: 궁성 내 대각선을 따라 **전진할 수 있다.** 역시 뒤로 이동할 수는 없다.

### 구현 순서

- 궁성 영역 정의
    - 궁성 내부 좌표 범위를 판별하는 기능이 필요하다.
    - 궁성 대각선 위의 좌표를 판별하는 기능이 필요하다.
- 장, 사 이동 구현
    - 궁성 범위를 벗어나면 이동할 수 없다.
    - 대각선 이동은 대각선 위의 좌표에서만 가능하다.
- 차, 포 궁성 내 대각선 이동 구현
    - 출발지와 도착지가 모두 궁성 내부일 때 대각선 이동이 가능하다.

## 승리 판정

- 상대 궁을 잡으면 승리한다.
    - 기물 이동 후 상대 궁이 보드에 존재하지 않으면 게임이 종료된다.
    - 궁을 잡은 나라가 승리한다.
- 점수 판정
    - `score` 명령 입력 시 양측 남은 기물의 점수를 계산하여 승패를 결정한다.
    - 한나라(후수)에게는 1.5점의 덤이 주어진다.
- 게임 저장 후 나가기
    - `quit` 명령 입력 시 현재 게임 상태를 DB에 저장하고 종료한다.
    - 다음 실행 시 이전 게임을 이어서 진행할 수 있다.

  (인터페이스)에 의존하여 DIP를 지키고 있다.

#### DB 변경 시 도메인 코드 영향 분석

- **DB 스키마 변경 시**
    - 컬럼 추가/이름 변경을 하는 경우
    - JanggiRepositoryImpl`의 SQL과 Dto를 매핑하는 로직만 수정된다.
    - 도메인 코드는 변경할 일이 없다.
- **DB 종류 변경 시**
    - 예를 들어 H2에서 MySQL로 변경하는 경우
    - `DatabaseConfig`의 연결 정보와 `JanggiRepositoryImpl`의 SQL만 수정.
    - `JanggiRepository` 인터페이스와 도메인 코드는 변경되지 않는다.
- **저장 방식 변경 시**
    - JDBC에서 JPA로 변경하는 경우
    - JanggiRepository`의 새 구현체를 만들면 됨. 인터페이스와 도메인 코드 변경 없음.

#### 규칙 적용으로 변경한 코드

1. 서비스 계층 도입
   > (If-Then) 만약 저장/조회 로직이 게임 로직과 섞이면
   > <br> → 서비스 계층에서 저장소를 호출한다
    * 데이터베이스 액세스 책임이 기능에 추가되면서 이 책임을 컨트롤러가 가질지, `Janggi` 클래스가 가질지 고민해야 했다. 하지만 둘 중 하나가 데이터베이스 조작 책임을 가지기에는 이미 두 클래스 모두
      속성이 3개인 상태였다.
    * "도메인은 저장 방식을 모른다" 규칙에 따라 `Janggi`가 DB를 직접 호출하는 선택지는 제외했고, 컨트롤러에 두기에는 게임 상태(`gameId`) 관리까지 떠안게 되어 책임이 과해졌다. 이를
      분산시키기 위해 Service 계층을 도입했다.
    * 결과적으로 Controller → Service → Repository 의존 방향이 잡혔고, 도메인(`Janggi`, `Board`, `Piece`)은 저장소를 전혀 모르는 구조가 되었다.
2. `Optional<GameDto>` 반환

   → 아래와 같이 null을 처리하는 방법을 고려해 본다.
   >
   > (방법)
   > - null이 아닌 값을 주체로 사용한다.
   > - Optional을 사용한다.
   > - try-catch문을 사용한다.
   > - if 문으로 검증한다.

    * `findRecentGame()`은 저장된 게임이 없을 수 있는 DB 조회다. null 사용 지양 규칙에 따라 `Optional`을 반환하도록 설계했다.
3. `PieceType` 팩토리
   > (금지) 기물 타입을 문자열이나 enum으로 분기하지 않는다

    * DB에서 읽은 `piece_type` 문자열로 구현체를 복원할 때 switch/if 분기가 필요했다. "기물 타입을 문자열이나 enum으로 분기하지 않는다" 규칙에 따라, `PieceType`
      enum 각 상수에 `Function<Team, Piece>` 팩토리를 필드로 두어 분기문 없이 기물을 생성하도록 변경했다.
    * 새 기물 타입이 추가되더라도 enum 상수만 추가하면 되어 OCP를 유지한다.
4. 트랜잭션 단위 저장
   > (기준) 저장 시점 기준: 저장은 하나의 수가 완전히 끝난 시점과 게임을 시작/종료할 때만 발생한다. 이동 중이거나 유효성 검증 단계에서는 저장하지 않는다.

    * "저장은 하나의 수가 완전히 끝난 시점에만 발생한다" 규칙에 따라 `updateGame()`은 기물 삭제 → 위치 이동 → 턴 변경을 하나의 트랜잭션으로 묶었다.
    * 이동 중이나 유효성 검증 단계에서는 DB에 접근하지 않는다.
