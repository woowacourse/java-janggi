## 기능 요구 사항
### 1.1 단계 - 보드 초기화
- [x] 게임 시작 시 장기판과 전체 기물을 올바른 위치에 초기화한다.
  - [x] 사용자의 입력을 받아 마와 상의 순서를 정한다.
    - [x] 마와 상 사용자 입력은 턴 순서인 초 먼저 진행한다.
  - [x] 보드는 궁, 차, 포, 마, 상, 사, 졸 총 16개, 양측 합계 32개의 기물을 정해진 위치에 배치한다.
  
### 1.2 단계 - 기물 이동(궁성 제외)
- [x] 각 기물은 고유의 이동 규칙을 가진다.
- [x] 자기 팀 위치로는 이동이 불가능하다.
  - [x] 궁
    - [ ] 궁성 안에서만 존재해야 한다.
    - [x] 상하좌우로 한칸 이동한다.
    - [ ] 궁성 내에서 "대각선 연결이 존재하는 위치에서만" 대각선 이동이 가능하다.
  - [x] 차
    - [x] 상하좌우로 장애물을 만나기 전까지 이동할 수 있다.
    - [ ] 궁성 내에서 "대각선 연결이 존재하는 위치에서만" 대각선 이동이 가능하다.
  - [x] 포
    - [x] 기물 하나를 넘어 이동할 수 있다.
    - [ ] 궁성 내에서 "대각선 연결이 존재하는 위치에서만" 대각선 이동이 가능하다.
      - [x] 단, 포를 넘을 순 없다.
  - [x] 마
    - [x] 체스의 말처럼 상하좌우로 한칸 이동 후 대각선으로 이동한다. 
    - [ ] 궁성의 대각선을 활용할 수 있다.
      - [ ] 단, 한 칸 이동할 때 막혀다있면 이동이 불가능하다.
  - [x] 상
    - [x] 상하좌우로 한 칸 이동 후 대각선으로 두 칸 이동할 수 있다.
    - [ ] 궁성의 대각선을 활용할 수 있다.
      - [ ] 단, 도착지를 제외한 이동할 때 막혀있다면 이동이 불가능하다.
  - [x] 사
    - [ ] 궁성 안에서만 존재해야 한다.
    - [x] 상하좌우로 한 칸 이동한다.
    - [ ] 궁성 내에서 "대각선 연결이 존재하는 위치에서만" 대각선 이동이 가능하다.
  - [x] 졸은 상좌우로 한 칸 이동한다.

## 기능 단위 커밋 단위
### 1.1 단계 - 보드 초기화
- `Position` 기능
- `Place` 구현
- `Piece` 구현
- `Board` 초기화 

## 기초 설계
- Board - 보드 판 기물 위치 관리
- Game - 전체 게임, 플레이어 턴
- Place - 칸의 정보
- Piece - 기물 정보
- Position - 칸의 위치

## 설계 이유 

### Place 설계
- `Place`는 보드 칸의 정보를 의미합니다. `Empty` 혹은 `Piece` 구성됩니다.
- 처음 설계에서는 `Piece` 단일로 구성하였지만, `Piece` 안에 `Empty`가 있는 것이 맞지 않다고 판단했습니다.
- 그래서 `Place`는 인터페이스로 설계해 공통 사항인 `isEmpty` 메소드만을 정의하여 사용했습니다.

### Piece 설계
- 기물들은 나라(초/한)과 이동 전략을 공통으로 가지고 있어야 합니다
- `getSymbol()`은 `Piece`에서 구현할 수 없고 구체적인 자식 클래스(궁, 차 등)에서 반환해야 합니다.
- 따라서, 공통 사항은 구현해두고 `abstract method`로 자식 클래스에서 구현하도록 만들었습니다.


## 팀 단위 규칙
```aiexclude
1. 테스트 단위 기준

(If-Then) 만약 기능이 public 메서드로 외부에 노출되어 있다면 → 그 기능 단위로 테스트를 작성한다 (메서드 하나가 아니라, 하나의 기능을 구성하는 흐름 단위)
(If-Then) 만약 private 메서드를 직접 테스트하고 싶어진다면 → 클래스 분리 또는 접근제한자 재설계가 필요하다는 신호로 간주하고, 리팩터링을 먼저 검토한다
(If-Then) 만약 경계값이 존재하는 로직이라면 → 경계값 기준으로 테스트 케이스를 나눈다.

2. 테스트 제외 기준

(금지) 이번 미션에서 단순 getter/setter, DTO는 테스트하지 않는다 (public 메서드 테스트에 자연스럽게 흡수되는 것들)
(금지) 이번 미션에서 입출력(콘솔 I/O, 컨트롤러) 자체는 테스트하지 않는다 (유지보수성이 낮고, Mock 의존이 커지기 때문)
(If-Then) 만약 유틸/파싱 메서드에 비즈니스 규칙(도메인 규칙 + 형식 규칙)이 포함되어 있지 않다면 → 테스트에서 제외한다 (도메인과 무관한 단순 변환은 제외)


3. 테스트 어려움 대응

(If-Then) 만약 테스트 작성이 어렵다면 → 테스트 자체를 포기하지 않고, 설계에 문제가 있다는 신호로 받아들여 리팩터링을 먼저 진행한다
(If-Then) 만약 도메인 로직 안에 숨은 의존(랜덤, 시간, 외부 호출 등등)이 있다면 → 해당 의존을 바깥으로 꺼내 값으로 주입한 뒤 테스트한다.
(추가) 1시간 이상 걸릴시 ‘3. 테스트 어려움 대응' 보단 '4. 리팩터링 우선순위'을 준수한다.


4. 리팩터링 우선순위

1) 역할 분리
2) 숨은 의존성 제거 
3) 코드 가독성 향상(변수명, 중복 제거, 상수화 등)


5. 책임 분리 기준

응집도와 결합도를 기준으로 설계를 판단한다. 객체는 단일 책임을 가져야 하며, 변경 이유 역시 해당 책임과 일치해야 한다.
책임과 무관한 변경이 발생한다면 이는 잘못된 설계 신호로 보고, 역할을 분리한다.


6. 객체의 책임 할당

객체는 자신의 상태를 기반으로 스스로 행동하도록 책임을 가진다. 데이터를 꺼내 판단하지 말고 "묻지 말고 시켜라(Tell, Don't Ask)" 원칙을 따른다. 즉, 행동은 해당 정보를 가장 잘 아는 객체가 수행한다.

* 객체가 올바른 책임을 가졌는지 어떻게 아는가
* 클래스 상단의 import 문을 통해 책임 침범 여부를 점검한다.
* 도메인 객체가 UI, 입출력, 프레임워크 의존성을 가지면 책임이 섞인 신호로 판단한다.
* 일급 컬렉션이 담당해야 할 로직이 외부 서비스나 컨트롤러에 존재하지 않는지 확인한다.
* 도메인은 항상 도메인 규칙과 상태 관리에만 집중하도록 유지한다



7. 테스트와 설계 관련 규칙

* 테스트하기 어려운 코드는 설계도 의심해봐야 한다
* 테스트는 구현이 아니라 행위을 검증해야 한다
* 테스트를 위해 설계를 망치면 안 된다 (getter 남발, public 메서드, 원래 필요 없는 메서드를 노출)



8. 상태 위치 규칙 (어떤 상태를 어떤 객체가 가지는가)

* 기물은 이동 규칙만 담당하며 보드가 위치 유지 및 실질적인 기물 이동을 담당한다. 



9. 불변 객체 기준 (언제 불변으로 만드는가)

불변은 ‘참조 불변’과 ‘내용 불변’으로 나누어 생각할 수 있다.

참조 불변은 객체의 참조가 변경되지 않도록 하는 것이며,
주로 final 키워드를 통해 참조 재할당을 방지한다.
이는 컬렉션이나 배열과 같은 참조 타입을 다룰 때, 의도치 않은 참조 변경을 막기 위한 최소한의 안전 장치로 사용한다.

내용 불변은 객체의 내부 상태가 변경되지 않도록 하는 것이며,
참조 타입의 경우 setter나 상태 변경 메서드를 제거하여 내부 데이터 변경을 차단한다.
기본 타입 또한 값 변경이 필요 없는 경우 final로 선언하여 불변성을 유지한다.

이와 같이 참조와 내용을 분리하여 관리함으로써,
상황에 따라 부분적인 불변성을 적용할 수 있다.

10. 캡슐화 기준 (무엇을 숨기는가)

객체에 접근할 때 퍼블릭 인터페이스를 기준으로 접근한다. 
또한 캡슐화를 위해 상태를 외부로 노출하는 행위를 금한다.


11. null 사용 기준

null을 허용하게 되면 개발자의 검사 비용이 커지고 NullPointException 가능성이 생기기에 null 사용을 금한다. 

12. 조건문 대체 기준 (언제 다형성으로 바꾸는가)

확장 시 기존 코드를 수정해야 하는 문제가 발생한다.
이러한 경우 조건문을 다형성으로 대체하여, 각 객체가 자신의 책임에 따라 행동하도록 위임할 수 있다.


13. 역할/인터페이스 설계 기준

여러 동일한 책임이 있을 때 확장 가능한 설계를 위해서 역할(인터페이스)를 도입한다.


14. 새 타입 추가 시 변경 범위 제한 규칙

기물 추가 시 변경 범위는 다형성 추가 및 보드 초기화 시를 제외하고는 변경이 없어야 된다.
```
