## 2단계 - 기물 이동

- 2단계에서는 기물 이동 구현이 목적이니까 종료는 `Ctrl+C`로 강제 종료한다.

### 잘못된 기물 선택 시나리오

1. 다른 나라의 기물을 선택했을 때
   1. 예외: 다른나라의 기물 선택
   2. `[ERROR] 다른 나라의 기물을 선택할 수 없습니다.`
2. 기물이 없는 곳을 선택했다. (빈칸 or 장기판 외부)
   1. 예외: 기물이 없는 곳을 선택
   2. `[ERROR] 현재 위치에 존재하는 기물이 없습니다.`

### 기물 이동 규칙

- 궁성 영역 - 고려하지 않는다. (사이클 2)
- 기물 이동 규칙 공통
  - 현재 위치로 이동할 수 없다.
  - 보드 영역 밖으로 이동할 수 없다.
  - 목적지에 아군이 있으면 이동할 수 없다.
  - 목적지에 적군이 있으면 잡아낸다.

- `차`: 4방위로 이동한다.
  - 목적지까지의 경로에 기물이 있으면 이동할 수 없다.
- `포`: 4방위로 이동한다.
  - 무조건 목적지까지의 경로에 포를 제외한 기물이 하나만 존재해야 한다.
- `마`: 4방위 중 한 방향으로 한 칸 이동하고 대각선의 한 방향으로 1칸 이동해야 한다.
  - 목적지까지의 경로에 기물이 있으면 이동할 수 없다.
- `상`: 4방위 중 한 방향으로 한 칸 이동하고 대각선의 한 방향으로 2칸 이동해야 한다.
  - 목적지까지의 경로에 기물이 있으면 이동할 수 없다.
- `졸`: 직진과 좌, 우로만 한 칸 이동해야 한다.
  - 한 칸이라서 경로에 기물이 있을 리가 없다.
- `사, 장`: 궁성 영역이므로 구현하지 않는다.

## 미션 중 기록

### 상태 위치를 결정할 때 고민한 순간

게임의 현재 차례(turn)를 어디에 둘지 고민했다.

처음에는 Controller 자체에 turn 필드를 두는 것을 생각했다. 컨트롤러가 뷰와 도메인의 상호작용을 관리하는 곳이니 턴이라는 도메인의 전환도 컨트롤러에서 하는 것이 자연스럽다고 느꼈기 때문이었다.

그러나 턴은 *누가 움직일 수 있는가* 라는 게임 규칙에 해당하고, 컨트롤러는 뷰와 도메인의 연결만 담당해야 한다.
턴을 컨트롤러에 두면 게임 규칙이 컨트롤러에 새어나가게 된다. 결국 turn은 게임의 규칙을 관장하는 `Janggi`에 두기로 했다.

이렇게 하면 `Janggi`는 누가 움직일 수 있는지 판단하고, 이동이 완료되면 차례를 바꾸는 책임을 진다.

### 불변/캡슐화를 적용한 코드

Piece는 team과 type만 가지며, 모든 필드가 private final이다. 기물이 위치를 직접 가지면 이동할 때마다 내부 상태가 바뀌어 가변 객체가 된다.
위치를 Board의 `Map<Position, Piece>`로 분리함으로써
Piece 자체는 생성 후 상태가 변하지 않는 불변 객체로 유지했다.

### 규칙 적용으로 변경한 설계

> (기준) null 사용은 지양한다
>
> - (If-Then) 자바 API나 DB(외부자원)에 접근해야 하는 경우
> - -> Optional 또는 빈 객체를 고려한다.

`Board.movePiece()`에서 아군 확인 시 null 체크 대신 `Optional.ofNullable`을 적용해 해결했다.

```java
Optional.ofNullable(board.get(next))
        .ifPresent(otherPiece -> checkAlly(piece, otherPiece));
```

### 조건문을 다형성으로 대체한 코드

상차림 전략 선택에서 조건문 대신 Strategy 패턴과 Map을 사용했다.

조건문을 사용했다면

```java
if (formation == SANG_MA_SANG_MA) { 
  return new SangMaSangMaStrategy(); 
} else if (formation == MA_SANG_MA_SANG) { 
  ... 
}
```

이와 같이 if-else-if가 계속이어지는 코드를 구현해야 했다. 대신 `FormationFactory`에서 `Map<JanggiFormation, FormationStrategy>`로 전략을 등록하고, 상차림 유형별 조회하는 방식으로 대체했다.

```java
private static final Map<JanggiFormation, FormationStrategy> FORMATION_STRATEGIES = Map.of(
  SANG_MA_SANG_MA, new SangMaSangMaStrategy(),
  MA_SANG_MA_SANG, new MaSangMaSangStrategy(),
  ...
);
```

### 인터페이스/추상 클래스를 도입한 이유

FormationStrategy를 추상 클래스로 도입한 이유는 두 가지다.

1. 4가지 상차림은 "한나라 상차림 생성"과 "초나라 상차림 생성"이라는 공통 계약을 공유한다. 이 계약을 강제하기 위해 `generateHanFormation()`과 `generateChoFormation()`을 추상 메소드로 선언했다.
2. `generateFormation(Team team)` 메소드에서 팀에 따라 올바른 메소드를 호출하는 공통 로직이 있다. 이 로직은 모든 전략에서 동일하므로 추상 클래스의 구현 메소드로 두어 template method 패턴을 적용했다. 각 전략은 팀별 구체적인 좌표 배치만 구현하면 된다.

### 새 기물 추가 시 변경 범위?

용(DRAGON) 기물을 추가한다면

변경이 필요한 곳:

- `PieceType` - DRAGON 항목 추가
- `Dragon` - Piece를 상속, `comparePosition()`과 `extractPath()` 구현
- `BoardFactory` - 초기 배치에 `Minister` 추가
- `ViewMapper` - 화면 출력 기호 추가

변경이 필요 없는 곳:

- `Janggi.validateMovement()` - `piece.canMove()`에 위임하므로 변경 없음
- `Board.movePiece()` - 기물 타입을 알지 못하므로 변경 없음
- `FormationFactory`, `FormationStrategy` — 상차림 전략과 무관

변경 자체도 view부분을 제외하면 추가하는 방식으로 이어지기에 확장성 측면에서 개선했다.
