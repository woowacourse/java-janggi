### Switch
Switch 대체방법에 대해 고민해보라고 하셔서, 정리해보았습니다.

1)리스트 반환 Switch문 → Enum 으로 대체   
마상마상을 초기화할 때, 사용자 입력값에 따른 리스트 반환을 switch문으로 사용했습니다.    
이를 enum을 사용해서 사용자 입력 번호를 파라미터로 넣으면 Enum을 반환하도록 변경했습니다. (Masang.java 참고)    

2)객체 생성 Switch문 → Map+Factory로 대체    
switch를 대체할 수 있는 방법으로 enum과 Map+Factory을 고민했습니다.    
Enum의 필드 값으로 객체 생성을 둔다면, 새로운 상태가 추가될 때 도메인을 수정해줘야해서 OCP에 위반될 수 있습니다.   
또한, Enum은 컴파일 시점에 초기화되기 때문에 enum 내부에서 Piece 객체들이 생성될 때,    
PieceType enum이 초기화되지 않았다면 error가 발생할 수있습니다.   

그에 반해 Map은 그저 키값 하나를 추가해주면 되서 유지보수에 더 용이합니다.   
따라서, Map+Factory 형태로 switch 문을 대체했습니다. (PieceFactory.java 참고)

### 질문
**1. PieceFinder를 통해 Piece에서 Board 정보 조회하기**           
사이클 2에 들어와서, 각 기물에서 이동 규칙에 따라 한칸씩 이동하며 이동 가능한지 검증하는 방법으로 변경했습니다.

그래서 방법을 찾아보니, PieceFinder 인터페이스를 Board에서 구현하고, Piece에게 인터페이스를 파라미터로 넘겨주면, Piece가 인터페이스를 통해 Board의 정보를 가져오는 제어의 역전(IoC)이 된다는 답변을 받았습니다.
Piece에서 PieceFinder로 Board의 정보를 일부만 탐색하는 구조가 괜찮은지 궁금합니다.

(근데 이게 제어의 역전 개념이 맞을까요? Board가 Piece를 제어하는데, 인터페이스를 통해 Piece가 Board 정보를 가져오는 구조여서 제어의 역전이라고 이해했는데, 이게 맞는지도 궁금합니다.)

**3. DB Connection pool**      
DB Connection은 트랜잭션 단위로 열고 닫아야한다고 생각을 해서, Service의 메서드에서 매번 connection pool을 열고 닫는 코드가 되었습니다. 그러다보니 코드의 중복이 많아지는 것 같은데, 이를 효율적으로 리팩토링하는 방법이 있을지 궁금합니다.

**4. DB 기물 데이터 update 방법**   
현재는 사용자가 기물을 이동했을 떄, piece_position 테이블에서 해당 게임과 관련된 piece를 모두 삭제하고, 새로 insert하는 방식을 사용하고 있습니다.
delete하고 insert하는게 비효율적이라고 느껴지기도 하지만, 작은 규모에서는 해당 piece를 찾아서 update하는 것보다 delete + insert가 간단하고 데이터 정합성을 지키는데에 더 나을 거라고 생각이 드는데
 이에 대해 어떻게 생각하시는지 궁금합니다.


**5. 테스트 코드**    
기능이 많아지고, DB까지 추가하고 나니까 어느 테스트를 우선 시 해야할까에 대해 고민이 생겼습니다.
