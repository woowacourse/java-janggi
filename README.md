### 1-1. 보드 초기화

협력명: 장기판을 초기화 한다.

![img_1.png](img_1.png)

필요한 메시지(행동)

- 장기판을 초기화 하라
- 각 진영별 배치를 초기화 하라
- 진영별 배치를 선택하라
- 선택한 배치대로 기물들을 배치하라

#### 시나리오

1. 장기 게임을 초기화 한다. - JanggiGame
2. 진영별 배치를 선택한다. - Player
3. 진영에 맞는 기물 타입의 기물을 생성한다. - Piece
4. 각 진영별 기물 배치를 초기화한다. - Board

#### 각 메시지(행동)에 따른 책임을 부여한 객체

#### JanggiGame

- [x] 장기 게임을 초기화 한다.
- Board
- Players

#### Players

- [x] 각 플레이어별
- 진영 side ENUM

#### Player

- [x] 진영별 배치를 선택한다.
- 진영 side ENUM
- Board

#### Board

- [x] 각 진영별 기물 배치를 초기화한다.
- Map<Position, Piece>
- MAX_ROW
- MIN_ROW
- MAX_COLUMN
- MIN_COLUMN

#### Piece

- [x] 기물 타입의 기물을 생성한다.
- 진영 side ENUM
- 기물 종류 type ENUM

#### Position

- row
- column

### 1-2. 기물 이동

협력명: 장기 기물을 이동한다.

![img.png](img.png)

### 이동 규칙

공통 규칙

- 보드판을 벗어날 수 없다.
- 본인 진영의 말만 이동 시킬 수 있다.
- 상대 진영의 말이 있는 칸으로 이동하면 포획할 수 있다.
- 본인 진영의 말이 있는 칸으로 이동할 수 없다.

시나리오

이동 실패 케이스

1. 1,9에 초 진영의 차가 배치되어 있다.
2. 1,9의 초 진영의 차를 1,10 위치로 이동시킨다.
3. 이동에 실패한다.

이동 실패 케이스

1. 초 플레이어의 턴이다.
2. 10,9에 한 진영의 차가 배치되어 있다.
3. 초 플레이어가 10,9의 말을 이동시킨다.
4. 이동에 실패한다.

이동 실패 케이스

1. 초 플레이어의 턴이다.
2. 1,9에 초 진영의 차, 4,9에 초 진영의 졸이 배치되어 있다.
3. 초 플레이어가 1,9의 차를 4,9의 위치로 이동시킨다.
4. 이동에 실패한다.

- 끝에 도달하면 옆으로만 이동할 수 있다.

### 포

기본 조건: 말을 하나 띄어넘어 잡거나 이동할 수 있다.

- 궁궐 안에서는 대각선으로 이동할 수 있다.
- 뛰어넘는 상대 말이 포가 될수 없다.
- 포끼리는 잡을 수 없다.

구체적인 규칙

- Direction은 차 처럼 직선만 있어야 한다.
- 가는 경로에 기물이 1개만 있어야 한고, 해당 기물은 포가 아니여야 한다.
- 도착 경로에 기물은 포가 아니어야 한다.

### 필요한 메시지 (행동)

- 플레이어들이 번갈아가며 각 기물들을 이동하라 JanggiGame
- 한쪽 진영의 말을 이동하라 (시작위치 → 도착위치) Player
- 기물을 이동시켜라 (시작위치 → 도착위치) Board
- 시작 위치의 기물을 도착위치로 움직일 수 있는지 알려줘 Piece

### 고민 포인트

1. Board를 다 받아서 저장해야 할지, 변경된 부분만 전달할지?
   Board의 전체 상태를 받아서 저장하는 것이 좋다.
   변경된 부분만 추적해서 저장하려면 도메인 객체 안에 어떤 기물이 움직였는지 상태를 기억하는 로직 더티 체킹이 추가되어야 한다.
   이는 도메인 객체가 데이터베이스 저장을 위한 책임을 떠안게 되는 것을 의미하며, 도메인의 순수성을 해치게 된다.
2. Board에서 엔티티 객체로 from()으로 변경해서 저장할지?
   변환은 필요하지만, 그 위치가 Board의 내부여서는 안된다.
   Entity.from(), Board.toEntity()를 하게 되면 서로 의존하게 된다.
   즉, 구조가 바뀌어도 같이 변경이 일어나게 된다.

   결론은 repository 계층 내부에서 이루어져야 할거 같다.
   Board는 자신의 상태를 읽기 전용으로 반환하거나, DTO 형태로 내어준다.
   Repository는 이 데이터를 받아서 DB에 넣기 좋은 플랫한 데이터나 엔티티 객체로 변환한 뒤 SQL에 바인딩 한다.
3. DB에서 가져와서 비교(Diff)한 뒤 INSERT/UPDATE 할지?
   애플리케이션 단에서 직접 비교하는 것은 절대 비추한다.
   DB에서 데이터를 다 끌고와서 반복문으로 하나하나 비교하는 것은 코드를 매우 복잡하게 만든다.
   DB 통신 비용도 낭비된다.

   즉, UPDATE 쿼리 기능을 활용하자.
   있으면 수정하고, 없으면 추가한다.를 DB가 알아서 해준다.
   `ON DUPLICATE KEY UPDATE` 를 활용한다.
   DB에 고유키나 기본키로 설정되어 있어야 한다.
