# PR에 적을 내용

### 예외 메시지 풍부화 및 상수처리 여부

- 예외적인 입력값이 들어왔을 경우 해당 입력값을 같이 보여주며 예외가 발생했다는 것을 알려줘야 할지, 아니면 단순히 에러메시지만 보여줘야 할 지 궁금합니다.
- ex(올바르지 않은 입력값입니다. VS 3 5는 올바르지 않은 입력값입니다.)

- 예외 메시지를 처리할 때 관습적으로 상수처리를 해왔던 경험이 있습니다. 하지만, 예외 메시지를 전달하는 부분과 메시지가 함께 있는 경우가 더 직관적인 경우가 더 많았다고 생각합니다.
- 추가로 상수처리를 할 때 접근제어자를 private과 public중 어느 것을 써야 할지도 궁금합니다.

+ 개인의 의견 + 궁금함

### 인터페이스 확장 VS 메서드 파라미터 증가

졸과 병의 움직임을 구현하면서, 졸과 병은 바라보는 방향의 뒤로 움직임이 불가능한데,
이를 구현하기 위해선 SoldierStrategy에서 진영에 대한 정보를 알아야 했습니다.
이를 해결하기 위해서 아래의 세 가지 방법을 사용해보았습니다.

- PathChecker(Board의 interface) 내에 findCamp()라는 메서드를 두어서 캠프만 메시지로 뽑아온다.
- MoveStrategy의 move() 메서드의 파라미터로 Camp camp를 추가하여 파라미터를 늘린다.
- Strategy가 Camp라는 상태를 가지고 생성자로 주입받는다.

2번 방식의 경우에는 객체간의 메시지를 주고 받는 상황에서 move()라는 하나의 인터페이스가 오염된다고 생각했습니다.
왜냐하면 Camp에 관한 정보가 필요없는 기물들도 Camp에 접근이 가능하기 때문에, 좋지 않다고 생각했습니다.

3번의 방식은 행동 전략 자체가 기물의 상태에 의존적이기 때문에 기물의 움직임을 캡슐화 해놓고 행동에 대해서만 관리를 해야하는데,
camp라는 상태를 가지고 있는 것 자체가 어색하다고 생각했습니다.

따라서 인터페이스를 통해 다른 것은 건들지 않고 camp에 대해서만 접근할 수 있다고 판단했습니다.
또한 다른 전략들이 camp를 사용하지 않는다고 해도 인터페이스가 findCamp()메서드를 들고 있으면
다른 전략들에게 범용성을 넓혀준다고 생각하였습니다.

저와 페어의 기준에서는 이게 최선이라고 생각했는데, 리뷰어의 의견이 궁금합니다.

### Enum에 Switch-case 문을 사용하는 것을 지양해야 하는가?

enum의 경우에는 타입들이 지정되어 있으며, 이를 switch 문을 사용하였을 때,
사용하지 않는 경우나, 새로운 타입이 추가되는 경우 컴파일 단계에서 발견할 수 있어 편리하다고 생각했습니다.

개인적으로 저는 switch를 사용하지 말라는 말을, 비즈니스 로직의 경우에 조건 분기처리를 switch로
하지 말라는 말로 이해했고, 이 근거를 토대로 enum을 기반으로 switch문을 사용하는 로직들을 구축했습니다.
enum에 switch를 사용하는 것이 좋지 않은지 궁금합니다.

### 보드 초기화 하드코딩?

보드 초기화 자체는 장기에서 변하지 않는 룰인데 이를 초기화할 때 하드코딩하지 않고 다른 방법이 있는지 궁금합니다.
현재는 메서드와 알고리즘을 이용하여 보드 초기화 시 하드코딩하는 부분을 최소화하려고 했는데,
가독성 측면에서 접근하면 장기 도메인을 모르는 다른 사람이 봤을 때, 혹은 수정이 필요할 경우
하드코딩하는 방법이 직관성을 챙길 수 있는 방법이라고 생각하였습니다.

### static import enum 상수 사용

저는 개인적으로 static import를 활용해 enum 상수를 사용하는 것이 코드가 더 간결해진다는 느낌을 받았습니다.(특히 BoardInitializer)
다만 이 방식이 가독성을 해치지는 않는지,
또는 명시성이 떨어지거나 유지보수 측면에서 문제가 될 여지가 있는지 궁금합니다.
